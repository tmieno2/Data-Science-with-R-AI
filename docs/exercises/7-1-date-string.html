Ex-7-1: Dates and Text, with an AI Assistant

Abstract
Date and String

This is an in-class exercise. Before class, work through the lecture 07-1: Dates and Text. In class, you work through the worksheet with an AI assistant writing the code. Your job is everything the AI cannot do: knowing how the dates and names in the file are written, asking for the right thing and the right checks, and judging whether the result is right.

Setup

  1. Download the worksheet, ex-7-1.qmd, and the data file 7-1-grain-deliveries.csv.
  2. Make an R Project folder called ch7-practice, with two subfolders, data and analysis. You may ask the AI how to do this.
  3. Copy 7-1-grain-deliveries.csv into ch7-practice/data, and the worksheet into ch7-practice/analysis.
  4. Open the worksheet and start at Task 1.
It worked if

Typing here::here() in the Console prints the path to ch7-practice and nothing longer.

If here::here() prints a path ending in analysis, the .Rproj file was not recognised. here only accepts a .Rproj file whose first line starts with Version:, which every project created in RStudio (File, New Project) has. An empty .Rproj file made any other way does not count.

Answers

Open each one only after you have tried the task.

Task 1: Look and predict

What you should find

A. 421 lines: one line of column names and 420 data rows, one per truckload.

B. The first rows are written like 09/01/2025: a two-digit number, a slash, another, a slash, a four-digit year. Since the log starts on 1 September, that looks like month first. But line 6, a South row, says 01/09/2025, right after rows of 09/01/2025: the same day written the other way round. If you looked further, you may have seen a value such as 13/09/2025 (line 72), where the first number is above 12. Hold on to that; Task 3 is about it.

C. Within the first lines or a little further down, the crop column has Corn and corn, Soybeans and Soy beans, and popcorn. The farm column has ORTIZ AG beside Ortiz Ag, miller farms beside Miller Farms, and Schmidt Bros. beside Schmidt Bros.

Task 2: Dates as text

What you should find

The smallest and largest values of the text column are 01/09/2025 and 31/10/2025. Read month first, as the first rows suggest, the first is 9 January and the second is impossible (there is no month 31). They are the smallest and largest only because text is compared character by character from the left.

If you sorted by date as text, the first rows mix days from different months, all starting with 01/. The point: until the column is converted, a sort, a minimum, a maximum or a “group by month” on it is meaningless, and none of them gives an error.

Task 3: Convert the dates

What you should find

3a. If you told the AI the dates are month first, as the first lines suggest:

  • dates that failed to parse: expected 0, got 98
  • first and last date: expected 1 September to 30 November 2025, got 9 January 2025 to 11 December 2025
  • months with rows: expected 3, got 12

Three checks fail. 52 further rows got a date that is wrong but looks like a date: they did not fail, they just landed in the wrong month.

3b. All 98 failures, and all 52 dates outside the season, come from the South site (165 rows); none of the 255 North rows is affected. The South site writes dates day first: its first row says 01/09/2025, which is 1 September. Day first, a value such as 23/09/2025 has no month 23, so it failed; a value such as 05/10/2025 (5 October) was read as 10 May, so it landed outside the season with no warning at all.

The text-beside-date rows show it too, if one of them is from South.

A further 9 South rows are read wrong but stay inside the season: 10/09/2025, for example, is 10 September 2025 but was read as 9 October 2025. No check catches those. Only knowing how the South site writes dates fixes them, which is why 3c converts each site in its own order rather than just dropping the rows that failed.

3c. Parsed by site (North with mdy(), South with dmy()), every check passes: 0 failures, dates from 1 September 2025 to 30 November 2025, rows in September, October and November only.

If the AI used parse_date_time() with both orders instead, nothing fails to parse (0 failures), but 103 North rows are read day first, and the dates run from 9 January 2025 to 11 December 2025. The range and month checks show it; the failure count does not.

The checks, and why. Each one tied to a way this conversion could go wrong:

  1. Failures to parse: text in another format or order becomes NA with only a warning.
  2. First and last date: swapped day and month push dates outside the season.
  3. Rows in each month: swapped day and month put rows in months when no harvest happens.
  4. Text beside date: shows directly which way a value such as 05/10/2025 was read.

Only the first check catches the 98 failures; only checks 2 and 3 catch the 52 silent ones.

Task 4: Bushels per month

What you should find

September: 137,609; October: 137,320; November: 118,872 bushels. The three months add up to 393,801, the same as the total of the bushels column, 393,801, so no row was lost.

With the dates from 3a instead, there would be twelve months, and the 98 rows with a missing date would either show up as a month called NA or vanish from the table, depending on the code.

Task 5: Crop names

What you should find

5a. 9 distinct spellings before cleaning. The manager says there are three crops. After lower case and removing extra spaces: 4 values, corn, popcorn, soy beans, soybeans. The check “distinct crops: expected 3” fails, because soy beans has a space that soybeans does not. No change of case finds that; you have to see it in the list and say which spelling it should become. After that: corn, popcorn, soybeans.

5b. The search pattern "corn" matches corn and popcorn. Popcorn contains the letters corn. With that search pattern, corn deliveries add up to 244,333 bushels; the right answer, crop_clean == "corn" (or the search pattern "^corn$"), is 215,221. The difference, 29,112 bushels, is all the popcorn.

Only the check “distinct values the search pattern matched” shows this. The row count of the result looks fine, the total looks believable, and nothing warns you.

Task 6: Farm names (if you have time)

What you should find

13 distinct spellings before. After lower case and squishing spaces, 9, not the 8 farms the manager listed: schmidt bros and schmidt bros. are still two values (24 and 31 rows). A full stop is a character like any other.

If the AI fixed this by removing every . with the search pattern "." and not fixed(".") or "\\.", every farm name became empty text, which the distinct count (1 instead of 8) would show at once.

Task 7: Sam’s code

Answers

A. Reads the csv; converts date from text to dates, month first; keeps the rows whose crop, in lower case, contains corn; adds up bushels within each month name.

B. The path "data/7-1-grain-deliveries.csv" is relative to the folder R is in. At the Console of the project that is ch7-practice, so it works; inside a .qmd saved in analysis/ it is analysis, where there is no data folder, so rendering fails. here::here("data", "7-1-grain-deliveries.csv") works in both.

C. Three problems give wrong results without an error:

  1. Every South date is read month first: 54 corn rows get no date, and others land in the wrong month.
  2. tapply() silently leaves out rows whose month is missing, so the monthly totals add up to 193,842, not the 244,333 bushels of all the rows it selected.
  3. The search pattern "corn" also keeps popcorn.

(The months also come out in alphabetical order, April first, which is untidy rather than wrong.)

D. Failures to parse (expected 0); first and last date, or the number of months (expected September to November); the distinct crop values matched (expected only corn); the sum of the monthly totals against the total of the rows (expected equal).
