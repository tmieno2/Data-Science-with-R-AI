08-1: Communicating with Tables

How this lecture works

What you will and will not learn today

  • The plan
  • Directions

An AI assistant can turn any data into a table in seconds, and it knows every option of every table package. What it cannot do is:

  • know what the table is supposed to tell the reader
  • know who the reader is
  • decide which numbers the reader must compare
  • tell whether the numbers in the table are the ones you meant

Those are your job. So today is about:

  1. The concept: what a table is for, and the design choices that decide whether it tells the reader anything
  2. Reading code: recognising what a line of table code does, without memorising it
  3. Asking AI: what to put in a table request, including a standard every finished table must meet
  4. Checking: how to tell that the numbers in the table are right

This deck shows the code of the flextable package. Lecture 08-3 shows the same pattern in the gt package, and 08-2 covers regression tables.

  • Ask your AI assistant to install the flextable and gt packages if you have not already. Installing is a one-time step per computer.
  • The data on these slides is countrypops, which comes with the gt package, so there is no file to download.

Start from the message

A table or a figure?

Both exist to tell a reader something. They are good at different things:

Choose When the reader needs to Example
A figure see a pattern: a trend, a gap, a shape yields rising over twenty years
A table read exact values, or look up the one row they care about each county’s yield, so a farmer can find their own
A table compare a few numbers that a figure would not make clearer the average yield in three states

If the reader will only take away a pattern, a figure usually does it faster. If the reader will quote a number, or look one up, use a table.

One sentence and one reader

  • What you need
  • Why the AI cannot do this

Before any table, write down two things:

  1. The message: the one sentence the reader should take away. For example: “From 2000 to 2020, Papua New Guinea, Vanuatu and the Solomon Islands, all in Melanesia, grew fastest, and Tonga and the Federated States of Micronesia barely grew.”
  2. The reader: who will see the table and what they already know. For example: students in a development course who know the Pacific but have not seen these numbers.

Every design decision on the following slides is judged against that sentence and that reader.

Ask an AI for “a table of this data” and it shows every column of the data, in the order they are stored, with every decimal. That is a table of the data, not of a message. Nothing in it tells the reader where to look.

The AI can only design for a message if you give it one.

Grouping is another order: rows under a heading per region, countries ordered by growth inside each. It serves a message about the regions.

Alphabetical order serves a reader who will look up one row, in a long table: a county list that farmers search for their own county. For a message about which rows are largest or smallest, order by the value. For years, use time order.

  • Round to the digits the message needs. A difference the message talks about must still be visible after rounding.
  • The same number of decimals all the way down a column.
  • Numbers right-aligned, text left-aligned.
  • Big numbers in a unit the reader can read: “thousands” or “millions” in the header, or thousands separators (19,028,802).

Say what the numbers are

A reader who sees a number must know what it is without reading your code.

  • Headers in plain words, with units: “Growth, 2000 to 2020 (%)”, never growth; “Population (thousands)”, never pop_2020.
  • A title that says what the table shows: which units (countries), which numbers, which years.
  • Notes under the table for what does not fit in a header: the source of the data, how a computed column was computed, and how many observations are behind each number when that varies.

A header such as “Growth” can mean several things. The section “A table must be correct before it can communicate” shows two of them giving different numbers from the same data, and how a note prevents the confusion.

How table code is written

The pattern every table shares

Table code always has two stages. First, ordinary data code builds the display table. Then a table function turns it into a finished table, and a chain of steps changes one part of it at a time.

  • The pattern
  • Common steps
  • Variations you will see

Important

The steps change how numbers are shown (rounding, units, percent signs); which rows appear, their order, and the values are decided in the display table. A formatting step can still show a value wrongly (lecture 08-3 shows one that multiplies by 100), so check one shown value against the data.

display_table |>
  table_function() |>
  step_function(where, setting = value) |>
  step_function(where, setting = value)

Where a step applies is written j = (columns) and i = (rows) in flextable, and columns = and rows = in gt.

  • flextable::flextable(...): the package name, then ::, then the function, without loading the whole package.
  • The display table built in the same chain, straight into the table function: pacific |> pivot_wider(...) |> flextable().
  • The finished table stored under a name first (pop_ft <- ...) and printed on a later line.
  • modelsummary(...) for regression tables, which builds the display table for you (lecture 08-2).

One real example

The finished table for the message on “One sentence and one reader”. A sentence, then the chunk it describes, as you will see them in the HTML.

  • The code
  • The finished table

Build the display table: one row per country, the 2020 population in thousands (kept so the reader sees each country’s size), growth from 2000 to 2020 in percent, fastest growth first.

Code the AI wrote 
pop_table <- pacific |>
  pivot_wider(names_from = year, values_from = population, names_prefix = "pop_") |>
  mutate(
    growth = 100 * (pop_2020 / pop_2000 - 1),
    pop_2020 = pop_2020 / 1000
  ) |>
  arrange(desc(growth)) |>
  select(country_name, region, pop_2020, growth)

Turn it into a finished table: plain headers with units, whole numbers, a title, and notes on the source and on how growth was computed.

Code the AI wrote 
pop_ft <- pop_table |>
  flextable() |>
  set_header_labels(
    country_name = "Country",
    region = "Region",
    pop_2020 = "Population, 2020 (thousands)",
    growth = "Growth, 2000 to 2020 (%)"
  ) |>
  colformat_double(j = c("pop_2020", "growth"), digits = 0) |>
  set_caption("Population growth of 13 Pacific countries, 2000 to 2020, fastest first") |>
  add_footer_lines(c(
    "Growth: 2020 population divided by 2000 population, minus 1, in percent.",
    "Source: countrypops data in the gt R package."
  )) |>
  theme_booktabs() |>
  autofit()

What a finished table looks like

The table standard

Every table you hand in must meet this standard, whatever its message. Each item has a yes or no answer.

Item
1 Headers and row labels in plain words with units: “Growth, 2000 to 2020 (%)”, never growth
2 Categories in words, never codes such as 1
3 Rounded to what the message needs, the same number of decimals down each column
4 Thousands separators in large numbers, except in years
5 Percentages shown as percentages
6 Numbers right-aligned, text left-aligned
7 Text no smaller than the document’s body text
8 Fits the page width where it will appear, without scrolling
9 Rows in an order that serves the message; alphabetical only for a long table the reader searches
10 to 13 A title saying what the numbers are; notes on the source, on how any computed column was computed, and on the number of observations behind each value when it varies
14 Nothing the message does not need: no extra columns, row numbers, heavy borders, or colours that only decorate
15 to 18 For regression tables (lecture 08-2): one column per model; standard errors and their kind; stars left out or defined; observations for every model

The copyable version, to add to every table request, is in Recommended requests at the end of this deck.

A table must be correct before it can communicate

The numbers must be the ones you meant

  • Two meanings of “growth”
  • The check
  • Checks for any table

Ask an AI for “population growth by region” and either of these can come back. Both run without an error:

Code the AI wrote 
pacific_wide |>
  group_by(region) |>
  summarise(
    countries = n(),
    mean_of_countries = mean(growth),
    from_totals = 100 * (sum(pop_2020) / sum(pop_2000) - 1)
  )
# A tibble: 4 × 4
  region      countries mean_of_countries from_totals
  <chr>           <int>             <dbl>       <dbl>
1 Australasia         2              33.4        34.3
2 Melanesia           5              47.7        66.5
3 Micronesia          2              21.4        19.0
4 Polynesia           4              13.6        15.7
  • mean_of_countries: the average of the countries’ growth rates. Vanuatu, which had 192 thousand people in 2000, counts as much as Papua New Guinea, which had 5,508 thousand.
  • from_totals: the growth of the region’s total population.

For Melanesia, 48% against 66%. Neither is wrong; they answer different questions. A table headed “Growth (%)” does not say which one the reader is looking at.

Decide which one the message needs before you ask, and compute one value yourself from numbers you can see. Melanesia’s total population was 7,176,088 in 2000 and 11,945,398 in 2020, so the growth of the total is 66.5%. Then ask the AI to print the check:

Code the AI wrote 
growth_table <- pacific_wide |>
  group_by(region) |>
  summarise(growth = mean(growth))

cat("Melanesia growth: expected 66.5, got",
    round(growth_table$growth[growth_table$region == "Melanesia"], 1), "\n")
Melanesia growth: expected 66.5, got 47.7

The check fails: this code computed the average of the countries. Ask the AI to compute growth from the regional totals, and write in a note which one the table shows.

  1. Rows: the number of rows is the number of things the reader should see (here, 13 countries or 4 regions).
  2. One value, computed by hand: pick one cell and compute it yourself from the data.
  3. Counts behind each value: when a cell is an average, print how many observations it averages. A region with 2 countries and one with 5 look the same in a table of averages.
  4. Totals: if the counts should add up to the number of rows in the data, check that they do.

Judging a table

The checklist

Apply it to any table, yours or the AI’s, by looking at it in the rendered HTML. Each question has a yes or no answer.

  1. Can someone who has not seen the data state the message within a few seconds?
  2. Are the numbers the reader must compare next to each other, ideally down one column?
  3. Is every number one the message needs?
  4. Does every header say what its numbers are, with units?
  5. Does it meet every item of the table standard?
  6. Did one value, computed by hand, match?

A “no” to any question is something to fix.

Asking AI

Working with AI on your own research

Tables follow the same way of working as everything else (lecture 02-1, “Working with AI on your own research”): you ask, the AI writes into a Quarto document (.qmd) with one plain-English sentence above each chunk, you render it to HTML, and you judge the HTML.

For tables, judging the HTML matters even more:

  • The reader sees the finished table, not the data behind it. The HTML shows exactly what they will see.
  • The table sits next to the sentence that says what it shows, so you can check that the two agree.
  • The checks (rows, one value computed by hand) print right under the table.

Every table request ends with the table standard and then the closing instructions. Both are under Recommended requests.

What to put in a table request

The AI already knows every table package. Your request supplies what it cannot know:

  1. The data: which table or file, what one row is, and which columns the table uses, with their units
  2. The message: the one sentence the reader should take away
  3. The reader: who will see it, and what they already know
  4. The layout: what one row of the table is, which columns, and the order of the rows
  5. What each computed number means: “growth of the regional total”, not just “growth”
  6. The checks: the number of rows, and one value you computed yourself
  7. The table standard, then the closing instructions

Using an agent in your editor or terminal?

An agent such as Claude Code can open the data and look for itself. It still cannot know your message, your reader, or which meaning of a number you intend. Write those down before it runs.
