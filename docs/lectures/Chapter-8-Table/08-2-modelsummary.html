08-2: Regression Tables

How this lecture works

What you will and will not learn today

  • The plan
  • Directions

An AI assistant can estimate regressions and put them in a table in seconds. What it cannot do is:

  • know which models you meant to compare, and why
  • know which estimate your message is about
  • know how many observations each model should have
  • tell whether the table shows the models you meant

Those are your job. So today is about:

  1. The concept: what a reader needs from a regression table
  2. Reading code: recognising what a line of regression-table code does
  3. Asking AI: what to put in the request
  4. Checking: that the table shows the models you meant, with the observations you expected

This deck assumes lecture 08-1 (the message, the display table, the table standard). It does not teach regression itself: what an estimate or a standard error means is the subject of your econometrics course.

  • This lecture uses the modelsummary package. Install it if you do not have it yet; it is a one-time step per computer (see the packages slide in Chapter 1).
  • The data on these slides is airquality, which comes with R, so there is no file to download.

What a regression table is for

The data and the models on these slides

airquality has one row per day in New York, May to September 1973: 153 rows. The columns used here:

Column What it is
Ozone Ozone concentration (parts per billion)
Temp Maximum temperature (degrees Fahrenheit)
Wind Average wind speed (miles per hour)
Solar.R Solar radiation (langleys, a unit of sunlight energy per area)

The message: “Hotter days have more ozone, and the relationship holds after accounting for wind and sunlight.” So three models (regressions), each adding a variable:

m1 <- lm(Ozone ~ Temp, data = air)
m2 <- lm(Ozone ~ Temp + Wind, data = air)
m3 <- lm(Ozone ~ Temp + Wind + Solar.R, data = air)

lm() estimates a linear regression. To the left of ~ is the outcome (what the model explains); to the right, the variables that explain it.

What the reader needs from a regression table

A reader of a regression table is asking four questions. Each part of the table answers one:

The reader asks The part of the table that answers
Which models are these? What does each explain, with which variables? The column headers and title; which coefficient rows are filled in for each column
How large is the estimate the message is about? The coefficient rows (one per variable), in plain words with units
How precise is it? The standard error in parentheses below each estimate, and a note saying which kind of standard error
What data is behind each model? The number of observations at the bottom of each column, and notes on the sample

Anything that does not answer one of these questions is clutter for this reader. The comparison the message is about runs across the columns: here, how the temperature estimate changes as wind and sunlight are added.

How regression-table code is written

The pattern

A regression table function does the work of the display table (lecture 08-1) for you: it takes the estimated models and lays out one column per model. Every call follows the same pattern.

  • The pattern
  • Common options
  • Variations you will see
modelsummary(
  list("header 1" = model_1, "header 2" = model_2, ...),
  option = value, ...
)
Part What it is Required?
list(...) The models, one per column, in the order of the columns Yes, the only required input
"header 1" = The header of that column. Leave it out and the header is (1), (2), … No
option = value What to show and how: labels, which rows, standard errors, title, notes No; each has a default

The header is attached to the model by the = inside list(). Nothing checks that the header describes the model: list("Soybeans" = corn_model) gives a column called “Soybeans” with the corn results in it.

Option What it does Default if left out
coef_map = c("raw" = "Label") Renames coefficient rows, sets their order, and drops every coefficient not listed raw names, in the order the models have them
coef_rename = c("raw" = "Label") Renames only; keeps every coefficient raw names
gof_map = ... Which rows go at the bottom (observations, R squared) about eight rows
vcov = "HC1" Which standard errors the classical ones from lm()
fmt = 2 Number of decimals 3
align = "lrrr" Alignment, one letter per column: l left, r right centred numbers
stars = TRUE Adds significance stars and a note defining them no stars
title = "...", notes = "..." Title and notes none
output = "flextable" or "gt" Hands back a flextable or gt table, to change further with the steps from 08-1 a table for the document being rendered

msummary() is a shorter name for the same function.

  • modelsummary::modelsummary(...): the package name, then ::, then the function.
  • The list of models stored first under a name, models <- list(...), then modelsummary(models, ...).
  • Models from other functions in the same list, such as fixest::feols() for models with fixed effects (one constant per group, such as per county). The table code is the same.
  • modelsummary(...) |> some_step(): the table passed on to a styling step from 08-1, after output = "flextable" or "gt".

One real example

The “After” table, as you would see it in the HTML: a sentence, then the chunk.

Put the three ozone models side by side, with plain labels and the temperature row first, only observations and R squared at the bottom, robust standard errors, two decimals, a title and notes.

Code the AI wrote 
coef_labels <- c(
  "Temp" = "Temperature (°F)",
  "Wind" = "Wind speed (miles per hour)",
  "Solar.R" = "Solar radiation (langleys)",
  "(Intercept)" = "Constant"
)
modelsummary(
  list("(1)" = m1, "(2)" = m2, "(3)" = m3),
  coef_map = coef_labels,
  gof_map = list(
    list(raw = "nobs", clean = "Observations (days)", fmt = 0),
    list(raw = "r.squared", clean = "R squared", fmt = 2)
  ),
  vcov = "HC1",
  fmt = 2,
  align = "lrrr",
  title = "Ozone (parts per billion) and the weather, New York, May to September 1973",
  notes = c(
    "Each column is a linear regression of ozone on the variables listed. Robust standard errors (HC1) in parentheses.",
    "Days with a missing value in any variable a model uses are left out of that model.",
    "Data: airquality, which comes with R."
  )
)

You should be able to point at the part that sets each label, the part that decides which rows appear at the bottom, and the part that chooses the standard errors. The column order comes from the order inside list().

Standard errors

Which standard errors, and saying so

  • Same estimates, different standard errors
  • An option that does nothing

There are several ways to compute standard errors, and your econometrics course says which one a model needs. In the table, vcov = chooses. It changes the standard errors only, never the estimates:

Code the AI wrote 
modelsummary(
  list("Classical" = m2, "Robust (HC1)" = m2),
  vcov = list("classical", "HC1"),
  coef_map = c("Temp" = "Temperature (°F)", "Wind" = "Wind speed (miles per hour)"),
  gof_map = list(list(raw = "nobs", clean = "Observations (days)", fmt = 0)),
  fmt = 2
)
Classical Robust (HC1)
Temperature (°F) 1.84 1.84
(0.25) (0.20)
Wind speed (miles per hour) -3.06 -3.06
(0.66) (0.87)
Observations (days) 116 116

The estimates are identical; the standard errors in parentheses are not. A reader cannot tell which kind they are looking at unless a note says so.

Older code and older tutorials write statistic_override = instead of vcov =. That name no longer exists, and modelsummary() accepts it without an error or a warning, and ignores it:

Code the AI wrote 
modelsummary(
  list("Asked for robust" = m2),
  statistic_override = list(sandwich::vcovHC(m2, type = "HC1")),
  coef_map = c("Temp" = "Temperature (°F)", "Wind" = "Wind speed (miles per hour)"),
  gof_map = list(list(raw = "nobs", clean = "Observations (days)", fmt = 0)),
  fmt = 2
)
Asked for robust
Temperature (°F) 1.84
(0.25)
Wind speed (miles per hour) -3.06
(0.66)
Observations (days) 116

The standard errors are the classical ones from the previous tab, not the robust ones that were asked for. AI assistants learned from older code too, so they sometimes write this. The same happens with any option name modelsummary() does not know, such as a misspelling (vcovv =).

The check: for one model, print the table with and without the change of standard errors. If nothing moves, the change was not applied.

Checking the table

Does the table show the models you meant?

The AI can write the checking code. It cannot know which models you meant or how many observations each should have. Ask for these after every regression table:

Ask the AI to print Why What only you can supply
1 each column’s header next to its model’s formula A header is attached by position in list(), and nothing checks it describes the model which model goes in which column
2 the number of observations of each model Rows with a missing value are dropped without a word (next slide) the count you expect, from looking at the data
3 one estimate, straight from the model Confirms the table shows that model’s numbers which estimate the message is about
4 every coefficient each model has, against the rows in the table coef_map drops any coefficient it does not list which variables each model should have

Checks 2 and 4 catch failures that give no error at all. The next two slides show them.

Observations: what lm() drops without saying

  • The check
  • Why
  • What it means for the table

air has 153 rows. A student expects each model to use all of them, and asks the AI to print the check:

Code the AI wrote 
models <- list("(1)" = m1, "(2)" = m2, "(3)" = m3)
for (name in names(models)) {
  cat(paste0("observations in model ", name, ": expected ", nrow(air),
             ", got ", nobs(models[[name]])), "\n")
}
observations in model (1): expected 153, got 116 
observations in model (2): expected 153, got 116 
observations in model (3): expected 153, got 111

All three checks fail.

lm() leaves out every row with a missing value in any variable the model uses, and says nothing. Ozone is missing on 37 days and Solar.R on 7, some of them the same days:

Code the AI wrote 
cat(
  paste("days with Ozone and Temp:", sum(complete.cases(air[, c("Ozone", "Temp")]))),
  paste("days with Ozone, Temp, Wind and Solar.R:",
        sum(complete.cases(air[, c("Ozone", "Temp", "Wind", "Solar.R")]))),
  sep = "\n"
)
days with Ozone and Temp: 116
days with Ozone, Temp, Wind and Solar.R: 111

So the expected count is the number of rows with no missing value in any variable the model uses: 116, 116 and 111. Model (3) uses 5 fewer days than model (2).

When the columns use different rows, a change across the columns has two possible causes: the added variable, or the different days. Here the difference is small; in other data it can be large.

What to do, and to decide before you look at the estimates:

  • Say it in a note: “Days with a missing value in any variable a model uses are left out of that model”, with the number of observations shown for every column.
  • If the comparison across columns is the message, estimate every model on the same rows, those with no missing value in any variable of the largest model, and say so in a note.

Coefficients that disappear

coef_map renames coefficient rows and sets their order, and drops every coefficient it does not list. Here the AI was asked to label temperature and forgot wind:

Code the AI wrote 
modelsummary(
  list("(1)" = m1, "(2)" = m2),
  coef_map = c("Temp" = "Temperature (°F)"),
  gof_map = list(list(raw = "nobs", clean = "Observations (days)", fmt = 0)),
  fmt = 2
)
(1) (2)
Temperature (°F) 2.43 1.84
(0.23) (0.25)
Observations (days) 116 116

Column (2) is a model with wind in it, but the table shows no wind row and no constant, and nothing says they are missing. Sometimes leaving rows out is what you want (a note then says “also includes …”); it should never happen by accident.

The check: ask the AI to list each model’s coefficients next to the rows of the table, and to say which ones are not shown.

Summary statistics tables

The table that comes before the regressions

Papers usually show a table of the variables before the regressions: how many observations, the average, the spread, the range. The same package makes it, with a pattern of its own.

  • The pattern
  • One real example
datasummary(rows ~ columns, data = table)
Part What it is Required?
rows The variables, joined with +, one row each Yes
columns The statistics, joined with +: N, Mean, SD, Min, Max, Median Yes
data = table The data Yes

Swap the two sides of ~ and the variables become columns. datasummary_skim(table) is a shortcut that summarises every column with its own choice of statistics.

Code the AI wrote 
datasummary(
  Heading("Ozone (parts per billion)") * Ozone +
    Heading("Maximum temperature (°F)") * Temp +
    Heading("Wind speed (miles per hour)") * Wind +
    Heading("Solar radiation (langleys)") * Solar.R ~
    Heading("Days") * N + Mean + Heading("Std. dev.") * SD + Min + Max,
  data = air,
  fmt = 1,
  title = "Daily weather and ozone, New York, May to September 1973",
  notes = "Data: airquality, which comes with R."
)

Heading("...") * gives a row or column its label. The Days column is the check: it counts the days with a value, so it shows at once which variables have missing values, and it should match what you counted in the data.

Judging a regression table

The checklist

Apply it to any regression table, yours or the AI’s, in the rendered HTML. Each question has a yes or no answer.

  1. Can a reader tell, from the headers and title alone, what each model explains and how the models differ?
  2. Is the estimate the message is about easy to find (first row, plain label with units)?
  3. Does a note say which standard errors are shown, and define any stars?
  4. Is the number of observations shown for every model, and does it match what you expected?
  5. Did the printed formulas match the column headers?
  6. Is every coefficient each model has either shown, or mentioned in a note?
  7. Does it meet every item of the table standard?

Your turn: read the AI’s code

A student asked an AI to “make a regression table of my ozone models with robust standard errors” and kept this:

modelsummary(
  list("Temperature only" = m1, "Plus sunlight" = m2, "Plus wind" = m3),
  statistic_override = list(sandwich::vcovHC(m1), sandwich::vcovHC(m2), sandwich::vcovHC(m3)),
  coef_map = c("Temp" = "Temperature", "Solar.R" = "Sunlight")
)
  • Questions
  • Answers

A. What does each part of the call do?

B. Which header is wrong? (Look at how m2 and m3 were defined on “The data and the models on these slides”.)

C. Besides the headers, which two problems give a wrong table without any error?

D. Which checks from “Does the table show the models you meant?” would catch each problem?

A. list(...): the three models, one column each, with their headers. statistic_override =: meant to use robust standard errors. coef_map =: label the temperature and sunlight rows, and show only those.

B. m2 is temperature plus wind, and m3 adds sunlight to that. The headers “Plus sunlight” and “Plus wind” are on the wrong columns.

C. statistic_override is ignored, so the standard errors are the classical ones, not the robust ones asked for. And coef_map drops wind and the constant, so the reader sees a model labelled “Plus wind” with no wind row. (Also missing: units in the labels, a title, a note on the standard errors.)

D. Check 1 (headers against formulas) catches the swapped headers. Check 4 (every coefficient against the table’s rows) catches the missing wind row. Printing the table with and without the change of standard errors catches the ignored statistic_override.

Asking AI

Working with AI on your own research

Regression tables follow the same way of working as everything else (lecture 02-1, “Working with AI on your own research”): you ask, the AI writes into a Quarto document (.qmd) with one plain-English sentence above each chunk and renders it to HTML, and you judge the HTML.

For regression tables this matters because:

  • The models, the table and the checks sit in one document, so a header can be read next to the formula it describes.
  • When the data changes, rendering again re-estimates every model and rebuilds the table. No number is ever copied by hand.
  • Your advisor reviews the models by reading the HTML: what was estimated, on which rows, with which standard errors.

What to put in a regression table request

The AI already knows modelsummary. Your request supplies what it cannot know:

  1. The data: what one row is, the columns used, their units, and which have missing values
  2. The models: for each column, the outcome and the variables, in the order the columns should appear
  3. The message: which estimate the reader should look at, and the comparison across columns
  4. The standard errors: which kind, from your econometrics course or your advisor
  5. What to show: which coefficient rows, in which order and with which labels; which rows at the bottom
  6. The checks: the number of observations you expect for each model, headers against formulas, every coefficient accounted for
  7. The table standard, then the closing instructions
