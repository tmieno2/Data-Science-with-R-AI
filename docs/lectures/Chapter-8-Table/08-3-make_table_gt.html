Never type a number into a table

The table in your paper comes from code

  • What is needed
  • Why

Every number in a table in your paper should be written there by code, from your data, the same code that wrote the table in your HTML. Never copy numbers from the HTML or the Console into Word by hand.

It is done when you can change something upstream (the data, a definition, a model), render again, and every table in the paper changes with it, with no typing.

  • Copying makes errors, and nobody checks a number that “came from R”. A transposed digit or a row pasted one line off gives no warning.
  • Analyses change. An advisor asks for one more year of data or a different definition. With copied numbers, every table has to be retyped, and every retyping is another chance for an error.
  • The record. With code, the .qmd and its HTML say exactly where each number in the paper came from (lecture 02-1, “Working with AI on your own research”).

Where the reader sees the table

The table has to look right where the reader sees it, not only in your HTML. Which package and which way of saving depend on the destination:

Destination What works Notes
Your HTML report (.qmd rendered to HTML) gt or flextable, printed in a chunk What you have been doing
A Word document flextable, saved with save_as_docx(); or gt, saved with gtsave() Both make a real Word table that a coauthor can edit
A .qmd rendered to Word either package, printed in a chunk Check the result: not every part survives (see “Checking the saved table”)
A PDF through LaTeX gt (gtsave() to .tex), or modelsummary(output = "latex") Common in economics journals

flextable was built for Word and PowerPoint first; gt for HTML first. Both do the jobs in 08-1’s table “Common steps”. If your paper is in Word, flextable is the safer default; for an HTML report, either is fine. Use the one your coauthors and your AI already work with, and check the result.

The same pattern in gt

The pattern, in gt

gt follows the same two-stage pattern as flextable (lecture 08-1, “The pattern every table shares”): build the display table with data code, then turn it into a table and change one part at a time.

  • The pattern
  • One real example
  • The finished table
display_table |>
  gt() |>
  step_function(columns = ..., setting = value) |>
  step_function(columns = ..., setting = value)

Function names in gt begin with what they act on, which helps you read them:

Beginning What the function acts on Examples
cols_ columns: headers, alignment, width cols_label(), cols_align()
fmt_ how numbers are shown fmt_number(), fmt_percent(), fmt_integer()
tab_ a part of the table: title, notes, a header over several columns tab_header(), tab_source_note(), tab_spanner()
opt_ the whole table opt_stylize()

Where a step applies is written columns = and rows =.

The finished table from 08-1, written in gt. A sentence, then the chunk, as in the HTML:

Turn the display table into a finished table: plain headers with units, whole numbers, a title, and notes on the source and on how growth was computed.

A gt default that surprises

fmt_percent() shows a number as a percentage, and by default it multiplies by 100 first, because it expects a share such as 0.35. The growth column already holds percentages (77 for Papua New Guinea):

Code the AI wrote 
pop_table |>
  head(3) |>
  gt() |>
  cols_label(country_name = "Country", region = "Region",
             pop_2020 = "Population, 2020 (thousands)", growth = "Growth, 2000 to 2020") |>
  fmt_number(columns = pop_2020, decimals = 0) |>
  fmt_percent(columns = growth, decimals = 0)
Country Region Population, 2020 (thousands) Growth, 2000 to 2020
Papua New Guinea Melanesia 9,750 7,700%
Vanuatu Melanesia 312 6,227%
Solomon Islands Melanesia 691 6,075%

No error, and the table looks finished. Papua New Guinea’s population did not grow by thousands of percent.

  • The fix: fmt_percent(..., scale_values = FALSE), or keep the column as a share (0.77) and let fmt_percent() multiply.
  • The check: one value you computed by hand. You know Papua New Guinea’s growth is 77% (2020 population divided by 2000 population, minus 1); the table must say 77%.

Saving and checking the table

How saving code is written

Saving a finished table follows the same pattern as saving data (lecture 03-1, “How writing code is written”): a function, the table, and a path.

  • The pattern
  • Save, then read back
Package Shortest call The file it makes
flextable save_as_docx(table, path = "table.docx") Word; save_as_pptx(), save_as_html(), save_as_image() for others
gt gtsave(table, "table.docx") Word; the extension chooses the format, such as .html, .tex, .rtf
modelsummary modelsummary(models, output = "flextable") \|> save_as_docx(path = "table.docx") Word, through flextable. (output = "table.docx" also works, but needs the pandoc R package installed.)

As with data, a file that already exists at the path is replaced without asking, and in your project the path is built with here::here(), for example here::here("tables", "population.docx").

The only way to know what the file holds is to read it back. For a Word file, the officer package lists the text of every cell:

Code the AI wrote 
word_file <- file.path(tempdir(), "population.docx")
gtsave(pop_gt, word_file)

cells <- officer::docx_summary(officer::read_docx(word_file))
png_cell <- which(cells$text == "Papua New Guinea")
png_row <- cells$row_id[png_cell]
png_cells <- cells[cells$content_type == "table cell" & cells$row_id == png_row, ]
png_values <- png_cells$text[order(png_cells$cell_id)]

cat(paste0("growth of Papua New Guinea in the Word file: expected ", png_growth,
           ", got ", tail(png_values, 1)), "\n")
growth of Papua New Guinea in the Word file: expected 77, got 77

On these slides the file goes to a temporary folder (tempdir()), so that rendering the slides leaves no files behind. In your project it goes to a folder such as tables/.

Checking the saved table

  • What to check
  • A title that went missing

Open the saved file in the program the reader will use, and check:

  1. One number, against the HTML. Pick a cell and compare. The read-back on the previous slide prints it for you.
  2. The title and notes are there. Not every part of a table survives every route into Word.
  3. It fits the page. A table that fits a wide HTML page can run off a Word page.
  4. Change something upstream and render again. The file should change with it, with no typing.

When these slides were made, a .qmd rendered to Word that printed a flextable with a title set by set_caption() produced a Word table without the title, and no warning. The same table saved with save_as_docx() kept it, and a gt title set with tab_header() survived both routes.

If the title is missing, ask the AI to set it with the chunk options #| label: tbl-<name> and #| tbl-cap: "<title>" instead, which Word keeps (tested: without a label starting tbl-, the caption was dropped too).

Package versions change, so do not memorise which route loses what. Open the Word file and look: that is the check that does not go out of date.

Asking AI

What to put in the request

Everything from 08-1’s “What to put in a table request” (the data, the message, the reader, the layout, what each computed number means, the checks, the table standard), plus what only you know about where the table is going:

  1. The destination: an HTML report, a Word document, a PDF through LaTeX
  2. The package, if your coauthors or your document already use one
  3. The path of the file to save, inside your project
  4. The check in the destination: read the saved file back and print one value you know, next to the value in the HTML

Tip

Ask for the table to be printed in the HTML and saved to the file, from the same code. Then the HTML is the record, and the file is what goes into the paper.

A chat assistant cannot render: paste its chunks into your .qmd and render it yourself. An agent in your editor or terminal can do every step.

The same block as in lecture 08-1. Paste it into every table request, just before the closing instructions:

Every table must meet this standard:
1. Column headers and row labels in plain words with units, such as
   "Corn yield (bushels per acre)", never a column name such as
   corn_yield.
2. Categories in words, such as "Irrigated", never a code such as 1.
3. Numbers rounded to what the message needs, with the same number of
   decimals down each column.
4. Thousands separators in large numbers, except in years.
5. Percentages shown as percentages.
6. Numbers right-aligned so that the digits line up; text left-aligned.
7. Text no smaller than the document's body text.
8. Fits the page width where it will appear, without scrolling.
9. Rows in an order that serves the message (by value, or in time
   order), not alphabetical unless the reader will search a long table.
10. A title that says what the numbers are.
11. A note giving the source of the data.
12. A note saying how any computed column was computed.
13. The number of observations behind each value, when it varies.
14. Nothing the message does not need: no extra columns, no row
    numbers, no heavy borders, no colours that only decorate.
For regression tables, also:
15. One column per model, with headers or a title saying what each
    model explains.
16. Standard errors in parentheses below each estimate, with their kind
    stated in a note.
17. Significance stars left out, or defined in a note and used the same
    way in every table.
18. The number of observations for every model.
The table made under the heading "<heading>" goes into <the
destination, such as a Word document>. Using <gt or flextable>, print
it in the HTML and also save it as <path for the new file, such as
tables/name.docx>, from the same code. Then read the saved file back
and check <one value> (I computed <the value> myself), and check that
the title and every note are in the file.

Put the code in my Quarto document <path to your .qmd>, under the
heading "<heading>", as R code chunks. Above each chunk, write one
plain-English sentence saying what it does and why. Build every path
with here::here(); no setwd(), no absolute paths. Print each check on
its own line as "name of check: expected X, got Y". Render the document
to HTML.

Then open the file yourself, in the program the reader will use.
