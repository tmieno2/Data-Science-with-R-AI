07-1: Dates and Text

How this lecture works

What you will and will not learn today

  • The plan
  • Directions

Two kinds of column cause more quiet mistakes than any other: dates and text. An AI assistant can write the code that converts a date or cleans a text column. It knows every function. What it cannot do is:

  • see how the dates in your file are written
  • know whether 03/04/2025 means 4 March or 3 April
  • see every spelling of a name that occurs in your data
  • tell whether the result is right

Those are your job. So today is about:

  1. The concept: what a date is to R, and what pattern matching on text is, and what has to be true for each to work
  2. Reading code: recognising what a line of date or text code does, without memorising it
  3. Asking AI: what to put in your request
  4. Checking: how to tell whether the code the AI wrote did the right thing
  • This lecture uses the tidyverse, here and gt packages. Install any you do not have yet; it is a one-time step per computer (see the packages slide in Chapter 1). The tidyverse includes lubridate (dates) and stringr (text).
  • The examples use pizzaplace, a table that comes with the gt package: a year of orders from a pizza shop, one row per pizza sold, 49,574 rows. Its columns include date (the day of the order), name (the pizza, such as thai_ckn) and price. On these slides the table is called pizza.

Dates: the concept

A date stored as text, and a date stored as a date

A file stores a date as characters, such as 2015-01-01. When it is read into R, the column is still text (R says character): a row of characters that happens to look like a date. Only after it is converted is it a date (R says Date): a value that R knows is a day in the calendar. The two print almost the same. They do not behave the same.

  • What R sees
  • Sorting
  • Subtracting
  • Grouping by month
class(pizza$date)
[1] "character"
class(ymd(pizza$date))
[1] "Date"

ymd() converts text written year, month, day into a date. Converting is called parsing in R’s help pages and on these slides.

Three dates written month/day/year, sorted as text and as dates:

as_text <- c("12/15/2014", "01/03/2015", "06/20/2015")
sort(as_text)
[1] "01/03/2015" "06/20/2015" "12/15/2014"
sort(mdy(as_text))
[1] "2014-12-15" "2015-01-03" "2015-06-20"

Text is sorted character by character, from the left, so 01/... comes first whatever the year. The December 2014 date ends up last. No error. Only the dates sort in calendar order.

How many days from the first order to the last?

max(pizza$date) - min(pizza$date)
Error in max(pizza$date) - min(pizza$date): non-numeric argument to binary operator

Text cannot be subtracted, and R says so. As dates:

max(ymd(pizza$date)) - min(ymd(pizza$date))
Time difference of 364 days

To count orders per month from text, you would take the characters that hold the month. Characters 6 and 7 of 2015-01-15 are the month, 01. Characters 6 and 7 of the same day written 01/15/2015 are /2. It depends on how the text was written, and nothing warns you when it is wrong.

From a date, month() gives the month whatever the text looked like:

pizza |>
  mutate(date = ymd(date)) |>
  count(month = month(date)) |>
  head(4)
# A tibble: 4 × 2
  month     n
  <dbl> <int>
1     1  4232
2     2  3961
3     3  4261
4     4  4151

How date code is written

Date code comes in two kinds: code that parses text into dates, and code that uses dates once they exist. Each follows one pattern.

  • Parsing: the pattern
  • Every parser follows the pattern
  • Using dates: the pattern
  • Variations you will see
table_name <- table_name |> mutate(date_column = parser(text_column))
Part What it is Required?
mutate(...) Adds a column to the table, or replaces one with the same name Needed to keep the result in the table
date_column = The name of the new date column. Often the same name as the text column, which replaces it. Yes
parser The function that reads the text. In lubridate, its name gives the order of the pieces: ymd is year, month, day. Yes
text_column The text to parse Yes, the only required input

A real line that follows the pattern:

pizza_dated <- pizza |> mutate(date = ymd(date))
Text looks like Parser Package
2015-03-04 ymd(x) lubridate (tidyverse)
03/04/2015 (month first) mdy(x) lubridate
04/03/2015 (day first) dmy(x) lubridate
2015-03-04 11:38:36 ymd_hms(x) lubridate
03/04/2015 as.Date(x, format = "%m/%d/%Y") built into R

lubridate’s parsers do not care about the separators: mdy() reads 03/04/2015, 03-04-2015 and March 4, 2015 alike. What they need is the order.

as.Date() instead takes a format, written with codes: %Y four-digit year, %y two-digit year, %m month as a number, %b or %B month as a word, %d day.

Once a column is a date, two kinds of line are common: taking a part of each date, and arithmetic with dates.

Code What it gives
year(date), month(date), mday(date) the year, the month (1 to 12), the day of the month
wday(date, label = TRUE) the day of the week, as Sun, Mon, …
yday(date) the day of the year, 1 to 366
floor_date(date, "month") the first day of the date’s month, still a date, so months of different years stay apart
date2 - date1 the number of days between them
date + days(7) the date a week later
date %m+% months(1) the same day one month later (see “Adding a month” under “Dates: the silent failures”)

  • as.Date(x, "%m/%d/%Y"): base R; the format is the second input, named or not.
  • parse_date_time(x, orders = c("mdy", "dmy")): tries more than one order. It decides which order to use from the values themselves; the order you list them in decides only when the values do not. A value that fits both orders, such as 03/04/2025, can be read either way with no warning, and since nothing fails to parse, the count of failures stays at 0. Only the range of the dates and the rows per month reveal it. Ask why the AI used it.
  • mutate(across(c(start, end), mdy)): the same parser applied to several columns at once.

Date formats, and what 03/04/2025 means

  • Many ways to write one day
  • 03/04/2025
  • Two-digit years

All of these are 15 December 2010:

  • 2010-12-15 (the international standard, year first)
  • 12/15/2010 (the usual US order, month first)
  • 15/12/2010 (most of the rest of the world, day first)
  • Dec 15 10
  • 15 December 2010

The parser has to match the way your file writes them, and only looking at the file tells you which that is.

Month first, it is 4 March. Day first, it is 3 April. Both parsers accept it without complaint:

mdy("03/04/2025")
[1] "2025-03-04"
dmy("03/04/2025")
[1] "2025-04-03"

The text alone cannot tell you which is right. Two things can:

  • Who wrote it: US software and people usually write month first; most other countries write day first.
  • The other values in the column: a first number above 12 can only be a day. If a column holds 25/03/2025, it is written day first.

A two-digit year has lost its century, so the parser guesses one:

mdy("01/01/68")
[1] "2068-01-01"
mdy("01/01/69")
[1] "1969-01-01"

68 became 2068 and 69 became 1969. A birth year or a weather record from 1968 would land 100 years in the future. And a format that expects two digits reads only two of a four-digit year:

as.Date("03/04/2025", format = "%m/%d/%y")
[1] "2020-03-04"

The year 2025 was read as 20, so 2020. No error.

Dates: the silent failures

As with reading files (lecture 03-1), some failures stop with an error and some give a wrong result with no error. This deck calls the second kind silent failures. These are the common ones for dates.

  • Text that does not fit becomes missing
  • The wrong order
  • Adding a month

A value the parser cannot read becomes NA (missing). R gives a warning, not an error, so the code carries on:

ymd(c("2015-01-05", "Jan 5 2015", "2015-13-01"))
Warning: 2 failed to parse.
[1] "2015-01-05" NA           NA

The second value is written in another format; the third has a month 13. In a rendered document the warning is one short line that is easy to scroll past, and in a column of thousands you would not see the NAs at all. The check: count the missing values before and after parsing. Any increase is text that failed to parse.

If a column written day first is parsed month first, two things happen at once, and only one of them is visible:

day_first <- c("25/03/2025", "05/03/2025")
mdy(day_first)
Warning: 1 failed to parse.
[1] NA           "2025-05-03"

25/03/2025 has no month 25, so it becomes NA (the warning is visible). 05/03/2025 is accepted as 3 May instead of 5 March, a wrong date with no warning. The check: the range of the dates, and the number of rows in each month. Dates outside the period the data should cover, or months that should be empty, reveal it.

Adding a month to 31 January asks for 31 February, which does not exist:

ymd("2015-01-31") + months(1)
[1] NA
ymd("2015-01-31") %m+% months(1)
[1] "2015-02-28"

Plain + gives NA, without a warning. %m+% moves to the last day of the target month. If the AI builds dates by adding months, look at which operator it used, and count the missing values afterwards.

Text: the concept

What pattern matching is

  • Exact comparison
  • Pattern matching
  • Regular expressions

R compares text character by character. To R, these are four different values:

counties <- c("Lancaster", "LANCASTER", "Lancaster  County", "lancaster")
counties == "Lancaster"
[1]  TRUE FALSE FALSE FALSE

Only the first equals "Lancaster": case differs in two, and the third has more characters (including two spaces). So counting, grouping or joining on this column treats one county as four.

Pattern matching asks a different question: does the text contain a given sequence of characters, anywhere? The sequence is called the search pattern (in code, the input named pattern).

str_detect(counties, "Lancaster")
[1]  TRUE FALSE  TRUE FALSE

The third value now matches too, because it contains Lancaster. Pattern matching is how code finds rows by part of their text, replaces part of a value, or takes a value apart. For example, pizzas with chicken have ckn in their name:

unique(pizza$name[str_detect(pizza$name, "ckn")])
[1] "thai_ckn"    "bbq_ckn"     "southw_ckn"  "cali_ckn"    "ckn_pesto"  
[6] "ckn_alfredo"

A regular expression is a search pattern written in a small language in which some characters have a special meaning. "ckn" is a regular expression with no special characters, so it means just those three letters. With special characters, one search pattern can say more:

  • "^ckn": ckn at the start of the text
  • "ckn$": ckn at the end
  • "ckn|chicken": either one
unique(pizza$name[str_detect(pizza$name, "^ckn")])
[1] "ckn_pesto"   "ckn_alfredo"

The table of special characters is on the slide “Regular expressions”. You do not need to write regular expressions; you need to recognise that a search pattern is one, and to check what it matched.

How text code is written

Almost every function in stringr, the tidyverse package for text, starts with str_ and follows one pattern.

  • The pattern
  • Every function follows the pattern
  • Variations you will see
str_function(text, pattern, replacement)
Part What it is Required?
str_function What to do with the matches: detect, replace, extract, count, split Yes
text The text to work on, usually a column, always the first input Yes
pattern The search pattern, a regular expression saying what to look for, the second input Yes, for functions that look for something
replacement What a match becomes Only for str_replace() and str_replace_all()

A real line that follows the pattern, making pizza names readable:

str_replace_all("thai_ckn", "_", " ")
[1] "thai ckn"
Code What it gives
str_detect(text, pattern) TRUE or FALSE for each value: does it contain the search pattern?
str_count(text, pattern) how many times each value contains it
str_replace(text, pattern, replacement) the first match in each value replaced
str_replace_all(text, pattern, replacement) every match replaced
str_remove_all(text, pattern) every match deleted
str_extract(text, pattern) the part of each value that matched
str_split(text, pattern) each value cut into pieces where the search pattern occurs

Some take no search pattern, only the text: str_to_lower() and str_to_upper() (change case), str_trim() (remove spaces at the start and end), str_squish() (also turn runs of spaces inside into one), str_pad() (add characters until a set width, such as leading zeros), and str_c() (join pieces into one text).

  • filter(table, str_detect(name, "ckn")): keep the rows that match; mutate(name = str_to_lower(name)): change a column.
  • grepl("ckn", x), sub(), gsub("_", " ", x): the base R versions. Note the order: in base R the search pattern comes first and the text later.
  • str_detect(x, regex("corn", ignore_case = TRUE)): the search pattern ignores upper and lower case.
  • str_detect(x, fixed(".")): the search pattern is taken literally, with no special characters.

Regular expressions: characters with a special meaning

  • The table
  • A special character used by mistake
In a search pattern Means Example Matches
. any one character "c.n" can, con, c5n
^ the start of the text "^ckn" ckn_pesto, not thai_ckn
$ the end of the text "ckn$" thai_ckn, not ckn_pesto
[0-9] or \\d one digit "[0-9]" any value with a digit

And | means or: "veg|garden" matches text containing either word.

The two backslashes are how R writes one backslash inside quotes. They turn a special character back into an ordinary one.

Removing the dot from 3.5:

str_replace_all("3.5", ".", "")
[1] ""
str_replace_all("3.5", fixed("."), "")
[1] "35"

. means any character, so every character was removed, leaving empty text. No error. fixed(".") (or "\\.") means the dot itself. Text with ., (, +, $ or ? in it, such as Bros. or ($), needs this care.

Text: the silent failures

  • A search pattern that matches more than intended
  • A search pattern that matches less than intended
  • Only the first match

You want the pepperoni pizzas, and the AI uses the search pattern "pep":

unique(pizza$name[str_detect(pizza$name, "pep")])
[1] "pepperoni"    "peppr_salami" "pep_msh_pep"

peppr_salami is a pepper salami pizza. It contains pep too, so it is counted as pepperoni. No error, and a count or a total that is too large. The check: list the distinct values the search pattern matched, and read them.

Text that means the same thing but is written differently does not match:

crops <- c("Wheat", "wheat", "WHEAT", "Winter  wheat", "Barley")
sum(str_detect(crops, "wheat"))
[1] 2

Wheat and WHEAT were missed, because upper and lower case are different characters. The usual fix makes the text consistent first:

cleaned <- str_squish(str_to_lower(crops))
cleaned
[1] "wheat"        "wheat"        "wheat"        "winter wheat" "barley"

The check: the distinct values, with a count of each, before and after cleaning. Here 5 distinct values became 3. Whether that is right depends on what you know: is winter wheat its own crop, or wheat?

str_replace() changes the first match in each value; str_replace_all() changes every one:

str_replace("pep_msh_pep", "_", " ")
[1] "pep msh_pep"
str_replace_all("pep_msh_pep", "_", " ")
[1] "pep msh pep"

On a column where most values have one _, the first version looks right on every row you happen to look at. The check: a few rows before and after, including one with more than one match.

Asking AI

Working with AI on your own research

Dates and text follow the same way of working as everything else (lecture 02-1, “Working with AI on your own research”): you ask, the AI writes into a Quarto document with one plain-English sentence above each chunk and renders it, and you judge the HTML.

For dates and text, the HTML matters because the failures are silent. A warning that some values failed to parse is one line in the chat that scrolls away; in the HTML it sits under the chunk that caused it, next to the check that counts the missing values.

Every request that asks for code ends with the closing instructions, the same lines as in 03-1. The full text is under Recommended requests.

Look at the column before you ask

  • Why
  • Distinct values of a text column
  • Raw values of a date column

You cannot tell the AI how dates are written, or which spellings mean the same thing, without looking. Two things to look at:

  • Dates: a handful of raw values, from different parts of the file. Do they put the year, the month or the day first? Is any first or second number above 12? Is the year written with two digits or four?
  • Text: every distinct value, with how often it occurs. That is the only way to see every spelling.
pizza |> count(size)
# A tibble: 5 × 2
  size      n
  <chr> <int>
1 L     18956
2 M     15635
3 S     14403
4 XL      552
5 XXL      28

5 sizes, each spelled one way, so this column needs no cleaning. On a column typed by people, this list is where you find Corn, corn and CORN.

pizza$date[c(1, 20000, 40000)]
[1] "2015-01-01" "2015-05-24" "2015-10-21"

Year first, four digits, then month, then day: ymd(). Looking at rows from different parts of the file matters: the first few rows may not represent the rest.

What to put in your request

The AI already knows the functions. Your request supplies what it cannot know, most of it from looking at the data:

  1. The column: which table and column, and what it holds
  2. How it is written: for dates, the order of year, month and day, with an example value; for text, the spellings you found
  3. What you want back: a date column; or the one spelling each group should have, such as all lower case
  4. What you expect: the first and last date the data should cover, how many values fail to parse (usually 0), how many distinct values there should be after cleaning
  5. Ask for checks: missing values before and after, the range of dates, distinct values before and after, a few rows before and after (see “Checking the result”)
  6. The closing instructions

Using an agent in your editor or terminal?

An agent such as Claude Code can look at the column itself. Still write down how the dates are written and what range you expect before it runs, so you have something to compare against.

Checks that come from knowing the data

The checks above apply to any date or text column. The most useful checks come from what you know about this data.

  • A shop open every day?
  • Do the names agree with the type?

The date check found 358 distinct dates in a year of 365 days. A pizza shop may close on some days. Ask:

Using the table orders, list every day of 2015 that has no orders, with
its day of the week.

Put the code in my Quarto document analysis/dates.qmd, under the
heading "Days without orders", as R code chunks. Above each chunk, write
one plain-English sentence saying what it does and why. Build every path
with here::here(); no setwd(), no absolute paths. Print each check on
its own line as "name of check: expected X, got Y". Render the document
to HTML.

The AI’s code and what it printed. It makes every day of 2015 with seq() (a sequence of dates, one day apart), then keeps the days that do not occur in orders:

Code the AI wrote

no_orders <- every_day[!every_day %in% orders$date]
data.frame(date = no_orders, weekday = wday(no_orders, label = TRUE))
        date weekday
1 2015-09-24     Thu
2 2015-09-25     Fri

4 2015-10-12     Mon

6 2015-10-26     Mon

Christmas Day, four Mondays in a row in October, and two days in September. Believable closures, not a parsing problem. But a daily average over “every day of the year” must know these days are missing.

Every pizza with ckn in its name should have the type chicken, and no other pizza should:
