09-5: Spatial Joins: Matching Rows by Location

How this lecture works

What you will and will not learn today

  • The plan
  • Directions

You have a layer of wells and a layer of counties, and you want to know which county each well is in. Or you have nitrogen use by county and water quality by watershed, and you need them in one table. Neither layer has a column the other one shares. What they share is location.

An AI assistant can write the code that matches rows by location. What it cannot do is:

  • know which layer should keep one row per feature in your result
  • know whether a feature matching several others, or none, is a problem for your question
  • tell whether the matched table is right

So today is about:

  1. The concept: what a spatial join is, how it differs from the merge by a key column of lecture 03-3, and what decides the number of rows it returns
  2. Reading code: the pattern a join follows, and the summarising step that usually comes after it
  3. Asking AI: what to say so the result has the rows you want
  4. Checking: row counts before and after, features with no match, totals that must not change, and a map
  • Ask your AI assistant to install the sf, tidyverse and here packages if you have not already.
  • This lecture assumes lecture 09-1 (vector basics) and lecture 09-4 (spatial relations: intersects, within, within a distance), and the merges of lecture 03-3.
  • The data files used on these slides sit in the same folder as the slides, so a path here is just the file name. In your own project, paths are built with here::here() (lecture 03-1).

The concept

A spatial join matches rows by where they are

  • The idea
  • Compared with a merge by key column
  • An example

A spatial join adds the columns of one layer to the rows of another, matching each row to the features it has a spatial relation with (lecture 09-4), usually “intersects”.

  • The target layer is the one whose rows you keep: you want a result with one row per target feature, or close to it.
  • The source layer is the one whose columns are brought in.

For each target feature, the join finds the source features that pass the relation and copies their columns onto the target’s row.

In lecture 03-3, two tables were merged by a key column (a column that identifies each row, such as a county code) that both tables had. A spatial join is the same operation with a different matching rule:

Merge by key column (lecture 03-3) Spatial join
Rows are matched when the key values are equal the shapes pass a spatial relation
What both tables need the same key column shapes in the same CRS
Typical function left_join(a, b, by = "fips") st_join(a, b)
A row of a with no match kept, with missing values (NA) kept, with missing values (NA)
A row of a with several matches repeated once per match repeated once per match

The last two rows are the same in both. Everything you learned about unmatched rows and repeated rows in lecture 03-3 applies here. With locations, you count the matches of each target feature with lengths(st_intersects(target, source)) (lecture 09-4), before or after the join. st_join() has no relationship = or unmatched = option and never warns about many matches, so the printed checks are the only guard.

How many rows come back

The number of rows a join returns is decided by how many source features each target feature matches:

Each target feature matches Its rows in the result Typical case
exactly one source feature 1 a well (point) in counties (polygons) that do not overlap
none 1, with NA in the source’s columns a point outside every polygon
several one per match, each a copy of the target row a county (polygon) containing many wells; a watershed crossing several counties

So the same two layers give very different results depending on which is the target:

c(
  wells_as_target = nrow(st_join(wells, counties)),
  counties_as_target = nrow(st_join(counties, wells))
)
   wells_as_target counties_as_target 
              1000               1052

1000 wells, each inside one county: 1000 rows. 93 counties as target: 1052 rows, because a county with 50 wells appears 50 times, and the 52 counties with no well appear once each with NA for the well’s columns (1000 + 52 = 1052).

Important

Before any join, decide which layer is the target and what one row of the result should be. “One row per county with the number of wells in it” is not what st_join(counties, wells) returns; it needs a summarising step after the join (next section).

How the code is written

The join

  • The pattern
  • Variations you will see
  • A real example
joined <- st_join(target, source, join = st_relation, options)
Part What it is Required?
joined <- The result: target rows with source columns added Needed to keep the result
target The layer whose rows (and shapes) you keep, always first Yes
source The layer whose columns are added, always second Yes
join = The spatial relation No; the default is st_intersects
options dist = for distance relations; left = FALSE to drop unmatched target rows; largest = TRUE to keep only the source feature with the largest overlap No

The shapes in the result are the target’s. The source’s shapes are dropped.

  • st_join(wells, counties, join = st_within): a relation other than the default
  • st_join(yield_points, seed_points, join = st_is_within_distance, dist = 10): every source feature within 10 units of the CRS (lecture 09-4)
  • st_join(watersheds, counties, largest = TRUE): one match per target, the one it overlaps most
  • st_join(wells, select(counties, name)): only some source columns brought in
  • aggregate(wells["gw_extracted"], counties, FUN = sum): a join and a summary in one call (next slide), with the source first

Summarising after a join

  • The pattern
  • A real example
  • Area-weighted summaries

When the target matches several source features (a county with many wells), the joined table has several rows per target. To get one row per target, summarise by the target’s ID:

summary_table <- joined |>
  st_drop_geometry() |>
  group_by(target_id) |>
  summarise(new_column = summary_function(source_column))
Step What it does
st_drop_geometry() Removes the shapes. Summarising with shapes attached also merges the shapes of each group, which is slow and not needed
group_by(target_id) One group per target feature, by its ID column
summarise(...) One row per group: a count, a sum, a mean of the source’s columns

The result is an ordinary table, which goes back onto the target layer with the key-column merge of lecture 03-3: left_join(counties, summary_table, by = "countyfp").

Groundwater pumped per county:

gw_by_county <- st_join(counties, wells) |>
  st_drop_geometry() |>
  group_by(countyfp, name) |>
  summarise(
    n_wells = sum(!is.na(wellid)),
    gw_total = sum(gw_extracted, na.rm = TRUE),
    .groups = "drop"
  )
arrange(gw_by_county, desc(n_wells)) |> head(3)
# A tibble: 3 × 4
  countyfp name    n_wells gw_total
  <chr>    <chr>     <int>    <dbl>
1 121      Merrick      83   10551.
2 047      Dawson       77    9879.
3 079      Hall         76    9413.

n_wells = sum(!is.na(wellid)) counts the rows that matched a well. The slide on silent failures shows why n(), which counts rows, is wrong here.

When target and source are both polygons (a watershed crossing several counties), a plain summary gives every overlapping source feature the same weight, however small the overlap. To weight by area, cut first, then summarise:

pieces <- st_intersection(target, source) |>     # one piece per overlap (lecture 09-4)
  mutate(area = st_area(geometry))
pieces |>
  st_drop_geometry() |>
  group_by(target_id) |>
  summarise(weighted = sum(source_value * area) / sum(area))

Each piece is the part of one target feature inside one source feature, with the columns of both, so its area is the weight.

What has to be true

Conditions for a spatial join to be right

  • The conditions
  • With and without an error
  1. Both layers are in the right CRS, and the same one (lecture 09-1). A layer with a wrong CRS lies somewhere else, and matches nothing.
  2. The right layer is the target. It decides what one row of the result is.
  3. The relation matches the question (lecture 09-4): “in”, “overlapping”, “within 10 m”.
  4. You know how many matches each target should have: exactly one, at most one, or several. That decides whether a summarising step is needed and which checks to print.
  5. For polygons against polygons, you know whether size of overlap matters. If it does, the summary must be weighted by area.
  • If the two layers have different CRSs, st_join() stops with an error. Good.
  • Every other failure gives a table with no error: rows quietly multiplied, rows with NA where a match was expected, averages that count a sliver of overlap as much as the whole. The next slide shows each one.

Silent failures

  • Several matches multiply rows
  • No match still makes a row
  • A wrong CRS matches nothing
  • Every overlap counts the same

After st_join(counties, wells), each county appears once per well. Anything computed from the county’s own columns is now counted many times. Nebraska’s area, from the counties before and after the join:

area_km2 <- function(x) as.numeric(units::set_units(st_area(x), km^2))
c(before = sum(area_km2(counties)), after_join = sum(area_km2(county_wells)))
    before after_join 
  200052.3  2232722.6

200,052 km² before, 2,232,723 after: each county’s area added once per well. No error; a total that should not change did.

Counting wells per county with n(), which counts rows:

county_wells |> st_drop_geometry() |> count(name) |> filter(name == "Loup")
  name n
1 Loup 1

Loup County has 0 wells, but it still has one row in the joined table (with NA for the well’s columns), so counting rows says 1. Every county without a well is reported as having one. Counting non-missing well IDs, sum(!is.na(wellid)), gives the right number.

Suppose the wells’ coordinates (longitude and latitude) were labelled with the wrong CRS, here UTM zone 14N, when the layer was made (lecture 09-1). Transformed so the CRSs agree, the join runs without error:

wells_mislabelled <- st_set_crs(st_drop_geometry(wells) |>
  bind_cols(st_coordinates(wells)) |>
  st_as_sf(coords = c("X", "Y")), 26914)
joined_wrong <- st_join(st_transform(wells_mislabelled, st_crs(counties)), counties)
sum(is.na(joined_wrong$countyfp))
[1] 1000

All 1000 wells have no county. Read as metres in UTM zone 14N, numbers such as -98 and 40 put every well within a few metres of one spot on the equator, in the Pacific Ocean, far from any Nebraska county. The number of wells with no match is the check that catches it.

Watershed 07060004 (a hydrologic unit, or watershed, in Iowa) overlaps 8 counties. A plain join and mean gives each county the same weight:

round(sort(p_one$area / sum(p_one$area)), 3)
[1] 0.001 0.007 0.030 0.072 0.119 0.141 0.296 0.335

Those are the shares of the watershed in each county: the smallest is 0.1% of the watershed, yet it counts as one of 8 equal parts of the plain average. Plain mean of nitrogen rate: 216.9 lb/acre; weighted by area: 211.2. Here the two are close; with a large difference between a sliver county and the rest, they would not be.

Asking AI

Working with AI on your own research

The same way of working as on the slide of this name in lecture 02-1: you ask, the AI writes into your .qmd with one plain-English sentence above each chunk, you render, and you judge the HTML. For a join, judging the HTML means reading the row counts and the map, since a join that runs is not yet a join that matched the right rows. Every request for code ends with the closing instructions of lecture 03-1, under Recommended requests.

Before you ask: three numbers to write down

  • Why
  • For the wells and counties

A join’s result is right or wrong mostly by its number of rows, and you can only judge that number if you wrote down what it should be before the code ran. Look at both layers (the four checks of lecture 09-1, plus a map of the two together), then write down:

  1. What one row of the result should be: one well, one county, one watershed
  2. How many matches each target should have: exactly one, at most one, or several
  3. How many targets should have no match: often zero, sometimes some, and you should know why
  • One row should be one well, so the target is the wells, and the result should have 1000 rows.
  • Each well should lie in exactly one county, since counties do not overlap.
  • Every well in a Nebraska wells file should be in a Nebraska county, so zero wells without a county.

For “groundwater per county”, one row should be one county: 93 rows after the summarising step, with a count of 0 wells for some counties, and the county totals adding up to the total pumped by all wells.

What to put in your request

The AI knows st_join(). Your request supplies what it cannot know:

  1. The layers: file names, where they are, their CRSs, and the ID column of each
  2. The target: which layer’s rows you keep, and what one row of the final table is
  3. The relation: “inside”, “overlapping”, “within 10 m”
  4. What to do with several matches: keep all, keep the largest overlap, or summarise (count, sum, mean, area-weighted mean) by the target’s ID
  5. What to do with no match: keep with NA (the default) or drop, and how many you expect
  6. Checks: rows before and after, targets with no match and with several, a total that must not change, a map
  7. The closing instructions

Checks that come from knowing the data

The checks above apply to any join. What you know about the data gives stronger ones.

  • A feature you know. Pick one well, look up its county on a map, and ask for that well’s row.
  • A share that must be whole. For watersheds and counties, each watershed’s pieces should cover the whole watershed. If they do not, part of it lies outside the area your county data covers.
Code the AI wrote 
coverage <- st_intersection(huc, nitrogen) |>
  mutate(area = as.numeric(st_area(geom))) |>
  st_drop_geometry() |>
  group_by(HUC_CODE) |>
  summarise(covered = sum(area)) |>
  left_join(tibble(HUC_CODE = huc$HUC_CODE, total = as.numeric(st_area(huc))), by = "HUC_CODE")
cat("watersheds fully covered by county data: expected", nrow(huc), "got", sum(coverage$covered / coverage$total > 0.99), "\n")
watersheds fully covered by county data: expected 28 got 24

The check fails: 4 of the 28 watersheds are only partly covered, one of them only 29%, because they extend beyond Iowa and the nitrogen data covers Iowa counties only. An average nitrogen rate for those watersheds describes their Iowa part only. Whether that is acceptable is a decision about the research, not the code; the point is that you now know to make it.

Your turn: read the AI’s code

A student asked an AI to “get the average nitrogen rate for each watershed”, and got this:

huc_n <- st_join(huc, nitrogen)
avg <- huc_n |>
  group_by(HUC_CODE) |>
  summarise(n_rate = mean(nitrogen_rate))
  • Questions
  • Answers

A. What does each line do, and what is one row of huc_n? Of avg?

B. Watershed 07060004 overlaps 8 counties. How much does a county covering 0.1% of it count in its average?

C. What is slow about the second line, and how would you fix it?

D. Which watersheds’ averages describe only part of the watershed, and how would you find out?

A. The join gives one row per watershed-and-county overlap (224 rows from 28 watersheds); the summary gives one row per watershed, the plain mean of its counties’ rates.

B. Exactly as much as the county covering most of it: each of the 8 counties counts equally. An area-weighted mean (cut with st_intersection(), weight by area) fixes that.

C. The shapes are still attached, so summarise() also merges the shapes of each group. st_drop_geometry() before group_by() avoids it.

D. Those extending beyond the counties in nitrogen. Print, for each watershed, the share of its area covered by the pieces from st_intersection().
