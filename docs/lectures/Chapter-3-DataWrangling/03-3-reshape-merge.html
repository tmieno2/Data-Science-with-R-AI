03-3: Reshaping and Merging

How this lecture works

What you will and will not learn today

  • The plan
  • Directions

Two operations change how your data is spread over rows, columns and tables:

  • Reshaping rearranges one table, so that one row means something else
  • Merging combines two tables, by matching their rows

An AI assistant writes the code for both in a line or two. What it cannot do is:

  • know what one row of each of your tables is
  • know which columns identify a row, and whether they really do
  • know whether the same county, year or person is written the same way in both tables
  • tell whether the result has the rows it should

Those four are your job. So today is about:

  1. The concept: what long and wide are, what a merge is, and what has to be true for each to work
  2. Reading code: the pattern reshaping and merging code follows
  3. Asking AI: what to put in your request
  4. Checking: the row counts, unmatched rows and repeated keys that tell you whether it worked
  • You need the tidyverse package, installed in 03-1. It includes tidyr (reshaping) and dplyr (merging).
  • The examples use corn_yields.csv from 03-1: corn yields for Nebraska counties in 2008, one row per county and irrigation status. On these slides the file sits in the same folder as the slides, so the code uses just its name. FIPS, the county code, is read as text, as 03-1 recommended.

Reshaping

Long and wide

The same numbers can be laid out in two ways. Three counties from corn_yields.csv:

  • Long
  • Wide
  • Which one you need
# A tibble: 6 × 4
  FIPS  County_name Irrigated Yield
  <chr> <chr>           <dbl> <dbl>
1 31019 BUFFALO             0   173
2 31019 BUFFALO             1   182
3 31041 CUSTER              0   163
4 31041 CUSTER              1   182
5 31047 DAWSON              0   177
6 31047 DAWSON              1   180

One row is one county and one irrigation status. Each yield has its own row; the column Irrigated says which kind of yield it is.

# A tibble: 3 × 4
  FIPS  County_name yield_0 yield_1
  <chr> <chr>         <dbl>   <dbl>
1 31019 BUFFALO         173     182
2 31041 CUSTER          163     182
3 31047 DAWSON          177     180

One row is one county. The irrigation status has moved into the column names: yield_0 holds non-irrigated yields and yield_1 irrigated ones. Nothing in the data says that; you have to know it.

Neither layout is right in general. The one you need depends on the next step:

  • Wide when the next step compares values side by side within a row: “irrigated minus non-irrigated yield, for each county” is one mutate() on the wide table.
  • Long when the next step works on one column of values: “the average yield by irrigation status” is group_by() and summarise() on the long table, and most figures (Chapter 4) want long data.

So “reshape this table” is not a request. “Make one row per county, with one yield column per irrigation status” is.

How reshaping code is written

Reshaping goes in one of two directions, and the code for each follows its own pattern.

  • Long to wide
  • Wide to long
  • Variations you will see
wide_table <- long_table |>
  pivot_wider(names_from = column_with_new_names, values_from = column_with_values)
Part What it is Required?
long_table The table to reshape Yes
names_from = The column whose values become the new column names (here Irrigated) Yes
values_from = The column whose values fill the new columns (here Yield) Yes
every other column Used to decide which rows belong together in one wide row (here FIPS and County_name) Not written; all the remaining columns are used
names_prefix = and others Extra instructions, such as text put in front of the new names No

The last row is where most problems come from: the columns you did not mention decide what one row of the result is.

long_table <- wide_table |>
  pivot_longer(columns_to_stack, names_to = "new_name_column", values_to = "new_value_column")
Part What it is Required?
wide_table The table to reshape Yes
columns_to_stack The columns whose values go into one column, for example starts_with("yield_") Yes
names_to = The name of the new column that will hold the old column names No; the default is "name"
values_to = The name of the new column that will hold the values No; the default is "value"

A real example, the three-county table back to long:

three_wide |>
  pivot_longer(starts_with("yield_"), names_to = "Irrigated", values_to = "Yield")
# A tibble: 6 × 4
  FIPS  County_name Irrigated Yield
  <chr> <chr>       <chr>     <dbl>
1 31019 BUFFALO     yield_0     173
2 31019 BUFFALO     yield_1     182
3 31041 CUSTER      yield_0     163
4 31041 CUSTER      yield_1     182
5 31047 DAWSON      yield_0     177
6 31047 DAWSON      yield_1     180

The old column names are now values, and they are text: "yield_0", not the number 0. Turning them back into numbers is a separate step.

The same two operations have other names, from older packages and other styles:

Long to wide Wide to long Where from
pivot_wider() pivot_longer() tidyr (tidyverse), current
spread() gather() tidyr, older versions
dcast() melt() data.table and reshape2
reshape(direction = "wide") reshape(direction = "long") built into R

Whatever the name, look for the same three things: which columns become names, which hold values, and which identify a row.

What has to be true for a reshape to work

  • The conditions
  • A column that differs
  • A combination that repeats

For long to wide:

  1. You know which columns identify one row of the result (here, FIPS and County_name for one row per county).
  2. No other column differs within that row. Every column that is neither the identifier, nor the names column, nor the values column must have the same value on all the rows that are combined, or be dropped first.
  3. Each identifier and name appears only once. One county must not have two non-irrigated yields.

For wide to long, the main condition is that the stacked columns hold the same kind of value (all yields, in the same units).

Breaking condition 2 gives a wrong table with no error. Breaking condition 3 gives a warning. The next two tabs show both with corn_yields.csv.

Data item describes the row, and the description is different for irrigated and non-irrigated corn. Leave it in, and it becomes part of the identifier:

corn_wide <- corn |>

Checking a reshape

Why: a reshape changes the number of rows in a way you can work out before running it. If the count is wrong, the identifier was wrong.

Direction Expected rows Expected missing values
Long to wide the number of distinct identifiers (for one row per county: the number of counties) the identifier and name combinations that are not in the long table
Wide to long wide rows × the number of stacked columns the missing values in the stacked columns, unless the request says to drop them

For the table above: 85 counties after leaving out 31000, so 85 rows wide, and back to long 85 × 2 = 170 rows, of which 15 have a missing yield.

A third check needs no arithmetic: the total of the values does not change. The sum of all yields before and after a reshape must be the same, apart from missing values.

Code the AI wrote 
before <- corn |> filter(FIPS != "31000")
back_long <- corn_wide |>
  pivot_longer(starts_with("yield_"), names_to = "Irrigated", values_to = "Yield")
cat(
  paste("wide rows: expected", n_distinct(before$FIPS), "got", nrow(corn_wide)),
  paste("long rows: expected", 2 * nrow(corn_wide), "got", nrow(back_long)),
  paste("missing yields after: expected", sum(is.na(corn_wide$yield_1)), "got", sum(is.na(back_long$Yield))),
  paste("total yield: expected", sum(before$Yield), "got", sum(back_long$Yield, na.rm = TRUE)),
  sep = "\n"
)
wide rows: expected 85 got 85
long rows: expected 170 got 170
missing yields after: expected 15 got 15
total yield: expected 26231 got 26231

Merging

What a merge is

  • Matching rows by key
  • Merging and stacking

A merge (also called a join) adds columns from a second table to a first one, by matching rows that refer to the same thing: the same county, the same county and year, the same person.

The columns used to match are the key. A key has to identify each row: in a table with one row per county and year, the key is the county code and the year together.

The yields:

# A tibble: 3 × 3
  fips   year yield
  <chr> <dbl> <dbl>
1 31019  2008   173
2 31041  2008   163
3 31047  2008   177

The rainfall:

# A tibble: 3 × 3
  fips   year rain_mm
  <chr> <dbl>   <dbl>
1 31019  2008     510
2 31041  2008     480
3 31047  2008     530

Matching on fips and year puts each county’s rainfall next to its yield. (These rainfall numbers are made up for this example.)

# A tibble: 3 × 4
  fips   year yield rain_mm
  <chr> <dbl> <dbl>   <dbl>
1 31019  2008   173     510
2 31041  2008   163     480
3 31047  2008   177     530

How merging code is written

  • The pattern
  • Every join follows the pattern
  • Variations you will see
merged_table <- join_function(first_table, second_table, by = c("key_column_1", "key_column_2"))
Part What it is Required?
join_function Which rows to keep (next tab) Yes
first_table The table you start from; with a left join, every one of its rows is kept Yes
second_table The table whose columns are added Yes
by = The key columns, which must exist in both tables Without it, every column with the same name in both is used, and a message says which
relationship =, unmatched = Instructions to stop with an error if the tables are not as expected: a row matching more than one row, or a row that would be dropped No, but worth asking for (see “Checking a merge”)

The joins differ only in which rows they keep:

Join Keeps Rows of the first table with no match
left_join() every row of the first table kept, with the new columns missing (NA)
inner_join() only rows that match in both dropped
full_join() every row of both tables kept, with missing values on whichever side has no match
anti_join() rows of the first table that have no match; adds no columns (this is the check for unmatched rows)

left_join() is the usual choice: it keeps the table you started with and adds to it.

  • by = join_by(fips, year): the same keys, written without quotes.
  • by = c("fips" = "county_code"): the key has a different name in each table; the first name is in the first table.
  • first_table |> left_join(second_table, by = ...): the first table piped in.
  • Base R: merge(first_table, second_table, by = c("fips", "year"), all.x = TRUE), where all.x = TRUE makes it a left join.
  • data.table: second_table[first_table, on = .(fips, year)].

What has to be true for a merge to work

  1. The key is complete and identifies each row: every column needed (county and year), in every table where you assume one row per key. If the second table is meant to have one row per county, each county code must appear in it once.
  2. The key has the same values in both tables. The same county must be written the same way: "01001" in one table and 1001 in the other are different values.
  3. The key has the same type in both tables. Text in one and a number in the other gives an error in dplyr. In base R’s merge() it gives no error: the codes that lost their zeros simply fail to match.
  4. You know which rows should match. Every county in the first table, or only some?

Condition 3 is the only one that gives an error, and only in dplyr. If 1, 2 or 4 fails, R gives you a merged table with no error, and the table is wrong. These are the silent failures of merging; the next slide shows each with corn_yields.csv.

What goes wrong without an error

The task for all three tabs: start from a list of the counties in corn_yields.csv, one row per county, and add each county’s irrigated yield.

counties  <- corn |> distinct(FIPS, County_name)
irrigated <- corn |> filter(Irrigated == 1) |> select(FIPS, irrigated_yield = Yield)
c(counties = nrow(counties), irrigated = nrow(irrigated))
 counties irrigated 
       86        74

  • A key with no match
  • Leading zeros lost
merged <- left_join(counties, irrigated, by = "FIPS")
nrow(merged)
[1] 89

The list had 86 counties; the result has 89 rows. A left join should keep the rows of the first table, so where did 3 rows come from?

count(irrigated, FIPS) |> filter(n > 1)
# A tibble: 1 × 2
  FIPS      n
  <chr> <int>
1 31000     4

FIPS 31000 (OTHER (COMBINED) COUNTIES, several small counties reported together) has 4 irrigated rows. A row of the first table that matches 4 rows becomes 4 rows. No warning: dplyr warns only when rows repeat on both sides of the match. Any later sum or average over counties now counts 31000 four times.

sum(is.na(merged$irrigated_yield))
[1] 15
nrow(anti_join(counties, irrigated, by = "FIPS"))
[1] 15

15 counties have no irrigated yield in the file, so they get NA. That is correct here: those counties have no irrigated row. But the same NA appears when a match should exist and the key is written differently, and the table looks the same either way. Count the unmatched rows, and decide whether the number is believable.

With inner_join() instead, the same 15 counties disappear from the result, again with no message.

A second table read with read.csv(), which, as in 03-1, turns 01001 into a number:

yields <- tibble(fips = c("01001", "01003", "31019"), yield = c(150, 162, 173))

01003,0
31019,1")
drought$fips
[1]  1001  1003 31019

Joining now stops with an error, because one key is text and the other a number (condition 3). The usual fix an AI suggests is to turn the number into text:

drought$fips <- as.character(drought$fips)
left_join(yields, drought, by = "fips")
# A tibble: 3 × 3
  fips  yield weeks
  <chr> <dbl> <int>
1 01001   150    NA
2 01003   162    NA
3 31019   173     1

The error is gone, and so are the two Alabama matches: "1001" is not "01001". No error, no warning, just missing values. The right fix is to read the key as text in the first place, or to put the zeros back.

Checking a merge

  • The checks
  • Making the code stop
  • Reading the HTML

The AI can write the checking code. It cannot know the right answers. Ask for these with every merge:

Ask the AI to print What it catches What only you can supply
1 the rows of each table, and of the result a repeated key (more rows), an inner join dropping rows (fewer) the number of rows the result should have
2 the keys that appear more than once, in each table the cause of extra rows which table should have one row per key
3 the number of rows of each table with no match in the other keys written differently; rows you did not expect to match how many should fail to match, and why
4 the number of missing values in the added columns unmatched rows, seen from the result the same
5 the type of the key in each table, and a few of its values lost leading zeros, text against numbers how the key should look

Two options make a join stop with an error instead of continuing silently. Ask for them when you know what to expect:

  • relationship = "many-to-one": stop if a row of the first table matches more than one row of the second
  • unmatched = "error": stop if a row would be dropped. In left_join() that means a row of the second table that matches nothing, since every row of the first table is kept anyway. To stop when a row of the first table has no match, ask for inner_join(..., unmatched = "error"), or for a check that stops when the number of unmatched rows is not 0.
left_join(counties, irrigated, by = "FIPS", relationship = "many-to-one")
Error in `left_join()`:
! Each row in `x` must match at most 1 row in `y`.
ℹ Row 18 of `x` matches multiple rows in `y`.

Here the code stops at 31000 instead of quietly adding rows.

For the county list, the student expected 86 rows after the join (one per county), one row per county in irrigated, and, having counted 71 distinct county codes among the irrigated rows, 86 − 71 = 15 counties without an irrigated yield. Stacking tables

Stacking puts one table under another. It is the step that combined the two sheets of corn_yields.xls in 03-1. It needs the two tables to have the same column names and types. When a name differs, R does not refuse:

sheet_08 <- readxl::read_excel("corn_yields.xls", sheet = "corn_yields_08")
sheet_09 <- readxl::read_excel("corn_yields.xls", sheet = "corn_yields_09") |>
  rename(yield = Yield)
stacked <- bind_rows(sheet_08, sheet_09)
dim(stacked)
[1] 322  10

Here the 2009 sheet’s Yield column was renamed yield, the kind of difference two files from different sources often have. bind_rows() keeps both as separate columns, so the result has 10 columns, and each of the two yield columns is missing in half the rows. The row count, 322, looks right.

Checks for stacking: the rows add up (161 + 161); the number of columns is the same as in each table (9); no column is missing in exactly the rows of one table.

Asking AI

Working with AI on your own research

The same way of working as on the slide of this name in lecture 02-1: you ask, the AI writes into your .qmd with one plain-English sentence above each chunk and renders it, and you judge the HTML. For reshaping and merging, judging the HTML is mostly reading row counts, which you can do only if you wrote down the numbers you expected before asking. Every request for code ends with the closing instructions, under Recommended requests.

Look at both tables before you ask

For a merge, look at each table and answer four questions in writing:

  1. What is one row? One county? One county and year?
  2. Which columns identify a row, and do they really? Count the rows per key value; any count above 1 is a repeat.
  3. How is the key written? Its type, its length, whether codes have leading zeros, and whether the two tables identify a row with the same columns at all. One table may use a county name where the other uses a county code, or a date where the other uses a year.
  4. Which rows should match? The same counties and years in both, or only some?

The answer to question 2 for the irrigated yields:

count(irrigated, FIPS) |>
  count(n, name = "number_of_codes")
# A tibble: 2 × 2
      n number_of_codes
  <int>           <int>
1     1              70
2     4               1

70 county codes appear once and one appears 4 times. That one row of output, read before asking, predicts the extra rows of the merge.

For a reshape, questions 1 and 2 are the whole job: what one row is now, what it should be after, and which columns identify it.

What to put in your request

The AI already knows the functions. Your request supplies what it cannot know:

  1. Each table: its name and what one row of it is
  2. The key: which columns identify a row in each table, how they are written, and whether they need to be built or converted before they can match
  3. What you want back: what one row of the result is, and which rows to keep (all rows of the first table, or only matches)
  4. What you expect: the number of rows of the result, and how many rows should fail to match
  5. Ask for checks: row counts, repeated keys and unmatched rows (see “Checking a merge”)
  6. The closing instructions: which .qmd and heading the code goes under, a sentence above each chunk, paths built with here::here(), checks printed as expected and got, and render to HTML

Checking the result

Checks that come from knowing the data

The checks on “Checking a merge” found that FIPS 31000 repeats. They cannot say what to do about it. Knowing the data can.

The name, OTHER (COMBINED) COUNTIES, says this code is not a county. The US Department of Agriculture reports counties with few farms together, one combined row for each of its crop reporting districts (groups of neighbouring counties). So the six rows belong to several districts, and the file has no column saying which. So:

  • In a table meant to have one row per county, these rows do not belong. Leave them out, and say so in the sentence above the chunk.
  • If you need them, you need the district, which means going back to the source, not changing the code.

Any time a key repeats, look at the repeated rows before deciding. They may be exact copies (keep one), corrections (keep the latest, if you can tell), or different things sharing a code, as here (no code change fixes it).

A. Reads the yields; reads the drought data; adds the drought columns to every row of yields, matching on county name and year; averages the yield.

B. state_name. County names are not unique across states: there is a Lincoln County in Colorado, in Kansas and in Nebraska. Without the state, Lincoln County, Nebraska in 2010 matches the drought rows of all three Lincoln counties in 2010.

C. Every row of a repeated name becomes several rows, so the result has more rows than yields, and the average counts those counties several times. Because the key repeats on both sides of the match, dplyr prints a warning about a “many-to-many relationship”; read warnings, do not ignore them. A second clue: state_name is in both tables but not in the key, so the result has two columns, state_name.x and state_name.y, which disagree on the extra rows.

D. The two read_csv() lines. A .qmd is rendered from its own folder, analysis, where there is no data folder (03-1, Condition 1). Paths built with here::here() fix it.

E. Rows of yields and of the result (more rows after a left join), and repeated keys in each table (county_name and year together repeat in both).
