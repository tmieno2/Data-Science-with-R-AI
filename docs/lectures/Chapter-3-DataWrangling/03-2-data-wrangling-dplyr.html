03-2: The Core Operations of Data Wrangling

How this lecture works

What you will and will not learn today

  • The plan
  • Directions

Once a table is in R, almost every analysis starts by changing it: keeping some rows, keeping some columns, adding a column, summarising by group, sorting. This is called data wrangling. An AI assistant writes the code for all of it without effort. What it cannot do is:

  • know which rows and columns your question needs
  • know how the values in your table are written, and what a missing value means
  • know what one row of the result should be
  • tell whether the result is right

Those four are your job. So today is about:

  1. The concept: the five operations, described in words, and what has to be true for each to do what you meant
  2. Reading code: the pattern all wrangling code follows, so you can read a chain of steps the AI wrote
  3. Asking AI: what to put in your request
  4. Checking: how to tell whether the code did what you asked
  • You need the tidyverse package, installed in 03-1. It includes dplyr, the package whose functions appear on these slides.
  • The examples use corn_yields.csv from 03-1: corn yields for Nebraska counties in 2008, one row per county and irrigation status. On these slides the file sits in the same folder as the slides, so the code uses just its name.

The concept

Five operations, in words

Almost every wrangling request is one of five operations, or several of them in a row. Say what you want in these words, and you have most of a request.

You want to Example request in words Rows after Columns after
A Keep rows that meet a condition “keep only the irrigated rows” fewer (or the same) the same
B Keep columns “keep only the county name and the yield” the same fewer
C Create a column from other columns “add the yield in tonnes per hectare” the same one more
D Summarise by group “the average yield for irrigated and for non-irrigated rows” one per group the groups and the summaries
E Sort “sort from highest yield to lowest” the same, reordered the same

The last two columns are a first check you can make without reading any code: if “keep columns” changed the number of rows, something other than what you asked for happened.

What one row is

Every table has an answer to “what is one row?” In corn_yields.csv, one row is one county, in one year, with one irrigation status. Operations A, B, C and E leave that answer unchanged. Operation D changes it: after “average yield by irrigation status”, one row is one irrigation status. Before asking for a summary, say what one row of the result should be.

How wrangling code is written

Whichever operation you ask for, the code the AI writes follows the same pattern.

new_table <- table_name |>
  operation(what to do, written with column names) |>
  operation(what to do, written with column names)
Part What it is Required?
new_table <- The name the result is stored under. Without it, the result is printed and then lost. Needed to keep the result
table_name The table you start from. It is never changed; the result is a new table. Yes
|> The pipe: “then”. It hands the table on its left to the operation on its right, as that operation’s first input. Needed when there are several steps
operation(...) A function that does one of the five operations Yes
inside the ( ) What to do, written with column names as they are, without quotes: a condition, a formula, a list of columns Yes

A real line that follows the pattern, with one step:

irrigated <- corn |>
  filter(Irrigated == 1)
nrow(irrigated)
[1] 74

74 of the 161 rows are irrigated.

Operation Function you will see Inside the ( ) Example
A Keep rows filter() a condition filter(Yield > 180)
B Keep columns select() column names; a minus sign drops a column select(County_name, Yield)
C Create a column mutate() new_name = formula mutate(yield_t_ha = Yield * 0.0628)
D Summarise by group group_by(), then summarise() the grouping columns; then new_name = summary group_by(Irrigated) |> summarise(avg = mean(Yield))
E Sort arrange() columns; desc() for largest first arrange(desc(Yield))

Others you will meet in AI-written code, each a variant of one of the five: rename() (change column names), distinct() (drop repeated rows), count() (number of rows per group, a short form of D), slice_max() (the rows with the largest values, A and E together), relocate() (move columns).

A condition is a statement that is true or false for each row; filter() keeps the rows where it is true. Conditions are written with these pieces:

Written Means Example
== is equal to (two equals signs) Irrigated == 1
!= is not equal to County_name != "BUFFALO"
>, >=, <, <= greater than, at least, less than, at most Yield >= 150
%in% is one of County_name %in% c("BUFFALO", "CUSTER")
&, or a comma and: both must be true Irrigated == 1 & Yield > 180
| or: at least one must be true Yield < 120 | Yield > 200
is.na() is missing is.na(Yield)
! not !is.na(Yield)

Text values go in quotes and must match exactly, capital letters included. Numbers go without quotes.

The same operations appear in other forms. They change how the code looks, not what it does:

  • %>% instead of |>. An older pipe from a package; for reading code, the two mean the same thing.
  • dplyr::filter(...): the package name, then ::, then the function, as in 03-1.
  • No pipe: filter(corn, Irrigated == 1). The table is the first input, which is exactly what the pipe supplies.
  • summarise(avg = mean(Yield), .by = Irrigated): the grouping written inside summarise() instead of in a group_by() before it.
  • Base R, without dplyr: corn[corn$Irrigated == 1, ] keeps rows, corn$yield_t_ha <- corn$Yield * 0.0628 creates a column, aggregate(Yield ~ Irrigated, data = corn, FUN = mean) summarises by group.

If you want all your code in one style, say so in your request (“use the tidyverse”).

Reading a chain of steps

AI-written code usually strings several operations together with the pipe. Read it top to bottom, saying “then” at each |>:

top_irrigated <- corn |>
  filter(Irrigated == 1) |>
  mutate(yield_t_ha = Yield * 0.0628) |>
  select(County_name, Yield, yield_t_ha) |>
  arrange(desc(Yield))
head(top_irrigated, 3)
# A tibble: 3 × 3
  County_name Yield yield_t_ha
  <chr>       <dbl>      <dbl>
1 PHELPS        204       12.8
2 CUMING        202       12.7
3 WAYNE         200       12.6

“Take corn, then keep the irrigated rows, then add the yield in tonnes per hectare, then keep three columns, then sort from the highest yield down.” (A bushel of corn is 56 pounds, so 1 bushel per acre is 0.0628 tonnes per hectare.)

The order of the steps matters

Each step works on the result of the step above it, not on the original table. Two examples:

  • Moving select(County_name, Yield) to the top gives an error, because the Irrigated column is gone by the time filter() looks for it.
  • Keeping the rows with a yield above 180 and then averaging gives a different number from averaging and then keeping rows. The code runs either way, so read the order and check it matches what you meant.

What has to be true for each operation to work

  • The conditions
  • Values written differently
  • Missing values in a condition
  • Missing values in a summary
  • One row per what?
  1. The column names are right. A wrong column name gives an error, which is the good case.
  2. The values are written the way the code assumes. A condition compares against values as they are stored: "BUFFALO" is not "Buffalo", and 1 is not "yes".
  3. Missing values are handled the way you meant. Each operation treats missing values in its own way, and none of them tells you.
  4. One row of the result is what you meant. Especially after summarising: one row per what?

If condition 1 fails, R stops with an error. If 2, 3 or 4 fails, R gives you a table and no error. This deck calls those the silent failures; the next tabs show one of each.

corn |>
  filter(County_name == "Buffalo") |>
  nrow()
[1] 0

No rows, and no error. The county names in this file are in capital letters, "BUFFALO", so nothing is equal to "Buffalo". The AI cannot know how your values are written unless it looks or you tell it.

A tiny table, written into the code, with one yield missing (NA, R’s mark for a missing value):

small <- tibble(
  county = c("A", "B", "C", "D"),
  yield  = c(150, 190, NA, 170)
)

Keep the rows above 160, and separately the rows at or below 160:

nrow(filter(small, yield > 160))
[1] 2
nrow(filter(small, yield <= 160))
[1] 1

2 + 1 = 3, not 4. County C is in neither: a condition on a missing value is neither true nor false, and filter() drops the row. Whether that is right depends on your question; the code never asks.

small$yield means the column yield of the table small.

mean(small$yield)
[1] NA
mean(small$yield, na.rm = TRUE)
[1] 170

Without instructions, the average of a column with a missing value is itself missing. With na.rm = TRUE (“remove missing values”), the average is over the 3 values that are there. The second looks fine, but it is an average of fewer values than you may think. If most of a group is missing, its average rests on a few rows, and the result does not say so.

Operation D is group_by() then summarise(). Swap summarise() for mutate() and the result looks similar but means something else:

by_status <- corn |>
  group_by(Irrigated) |>
  summarise(avg_yield = mean(Yield))
nrow(by_status)
[1] 2
with_avg <- corn |>
  group_by(Irrigated) |>
  mutate(avg_yield = mean(Yield))
nrow(with_avg)
[1] 161

summarise() gives one row per group. mutate() keeps all 161 rows and writes the group’s average on each one. Both are useful; they answer different requests. The number of rows tells you which one you got.

A second thing to watch: after group_by(), the table stays grouped until ungroup(), including after mutate() and, when there are two grouping columns, after summarise(). Every later step then works within each group, with no error. The printed table shows a # Groups: line when this is the case (summarise() also prints a message saying so; mutate() does not):

with_avg |>
  head(2)
# A tibble: 2 × 10
# Groups:   Irrigated [2]
   Year State FIPS  County_name State_name Commodity `Data item` Irrigated Yield
  <dbl> <dbl> <chr> <chr>       <chr>      <chr>     <chr>           <dbl> <dbl>
1  2008    31 31019 BUFFALO     NEBRASKA   CORN      CORN, GRAI…         0   173
2  2008    31 31019 BUFFALO     NEBRASKA   CORN      CORN, GRAI…         1   182
# ℹ 1 more variable: avg_yield <dbl>

Asking AI

Working with AI on your own research

The same way of working as on the slide of this name in lecture 02-1: you ask, the AI writes into your .qmd with one plain-English sentence above each chunk, you render, and you judge the HTML. For wrangling, judging the HTML means reading the chain of steps: does each sentence say what you asked for, and does the code under it do what the sentence says? Every request for code ends with the closing instructions, under Recommended requests.

Look at the values before you ask

  • Why
  • Which values a column takes
  • Missing values in each column

To write a condition, you need to know how the values are written. To ask for a summary, you need to know what the groups are and how many there are. To know what missing values will do, you need to know where they are. None of that is visible in the column names.

count() lists every value of a column and how many rows have it:

count(corn, Irrigated)
# A tibble: 2 × 2
  Irrigated     n
      <dbl> <int>
1         0    87
2         1    74

From this you learn: Irrigated is written as 0 and 1, not as “no” and “yes”, and a summary by irrigation status will have 2 rows, built from 87 and 74 rows.

colSums(is.na(corn))
       Year       State        FIPS County_name  State_name   Commodity 
          0           0           0           0           0           0 
  Data item   Irrigated       Yield 
          0           0           0

No missing values anywhere in this file, so missing values cannot change any result here. In most real data this line is not all zeros, and then it tells you which columns need a decision.

What to put in your request

The AI already knows the functions. Your request supplies what it cannot know, most of it from looking at the values:

  1. The table: its name, and what one row of it is
  2. The operation, in words, with the exact column names and the values as they are written (Irrigated is 1 for irrigated, County_name is in capital letters)
  3. Missing values: what to do with them in this step (leave them out, keep them, count them)
  4. What you want back: the name of the new table, and what one row of it is
  5. Ask for checks: the numbers you will compare against (see “Checking the result”)
  6. The closing instructions: which .qmd and heading the code goes under, a sentence above each chunk, paths built with here::here(), checks printed as expected and got, and render to HTML

A weak request and a strong one

Get the average corn yield by type.

The AI has to guess which table, which column means “type”, and whether you want one number per group or the average written on every row. If it guesses Commodity, which has one value in this file, it returns a single row: the code runs, and it answers a question you did not ask.

An example for the corn table:

Then check the number of rows of yield_by_status (I expect 2), and that
the numbers of rows behind the averages add up to the rows of corn (161).

Put the code in my Quarto document analysis/summary.qmd, under the

each chunk, write one plain-English sentence saying what it does and
why. Build every path with here::here(); no setwd(), no absolute paths.
Print each check on its own line as "name of check: expected X, got Y".
Render the document to HTML.

What the AI’s answer looks like in the rendered HTML: a sentence, then the chunk it describes, then what it printed.

Group the rows of corn by irrigation status, and for each group compute the average yield and count the rows.

yield_by_status <- corn |>
  group_by(Irrigated) |>
  summarise(avg_yield = mean(Yield), n_rows = n())
yield_by_status
# A tibble: 2 × 3
  Irrigated avg_yield n_rows
      <dbl>     <dbl>  <int>
1         0      158.     87
2         1      182.     74

Check that there is one row per irrigation status and that no row of corn was lost or counted twice.

cat("rows in yield_by_status: expected 2, got", nrow(yield_by_status), "\n")
rows in yield_by_status: expected 2, got 2 
cat("rows behind the averages: expected 161, got", sum(yield_by_status$n_rows), "\n")
rows behind the averages: expected 161, got 161

Both checks pass. n() counts the rows in each group; it takes no input. Irrigated corn averaged 182 bushels per acre and non-irrigated corn 158.

Checking the result

Checking: what to ask for, and why

  • Checks for each operation
  • Asking for them
  • Reading the HTML

The AI can write the checking code. It cannot know the right answers. These checks fit each operation:

Operation Ask the AI to print What only you can supply
A Keep rows the rows before and after; the values of the condition’s columns in the result; and, if missing values are possible, the rows kept plus the rows dropped how many rows you expect, from counting values first
B Keep columns the column names of the result which columns you need
C Create a column the smallest and largest value of the new column, its number of missing values, and one row you can work out by hand a believable range, and the hand calculation
D Summarise by group the number of rows of the result; the number of rows, and of non-missing values, behind each summary; that those add up to the original rows; whether the result is still grouped how many groups there are
E Sort the first and last rows which row should come first

Tell the AI what you expect, so the HTML says which checks passed:

I expect <number> rows after keeping <the rows you want, in words>, and
only the values <values you expect> in <the column in the condition>.
Print each check on its own line as "name of check: expected X, got Y".

You can fill in those blanks only if you counted the values first (under “Look at the values before you ask”). That part only you can do.

A student asked for the irrigated rows with a yield above 180, and the yield in tonnes per hectare. From count() they knew there are 74 irrigated rows, so they expected at most that many. They also looked up one county in the file before asking, Phelps, with an irrigated yield of 204, and worked out 204 × 0.0628 = 12.81 tonnes per hectare by hand. The AI wrote the code; in the rendered HTML, you read each line:

Code the AI wrote

  filter(Irrigated == 1, Yield > 180) |>

  paste("values of Irrigated: expected 1, got", paste(unique(high$Irrigated), collapse = ", ")),

  • No yield at or below 180 got through.
  • The new column matches the value for Phelps worked out by hand before asking.

Checks that come from knowing the data

The checks above apply to any table. The most useful checks come from what you know about this data.

In corn_yields.csv, two columns say the same thing in different ways: Irrigated is 1 or 0, and Data item is a description that contains the word IRRIGATED only for irrigated corn. If the file is right, the two always agree. So before trusting filter(Irrigated == 1), ask:

Using the table corn, count the rows for each combination of Irrigated
and whether Data item contains the word IRRIGATED. Print the counts as
one small table.

Put the code in my Quarto document analysis/summary.qmd, under the
heading "Do Irrigated and Data item agree?", as R code chunks. Above
each chunk, write one plain-English sentence saying what it does and
why. Build every path with here::here(); no setwd(), no absolute paths.
Print each check on its own line as "name of check: expected X, got Y".
Render the document to HTML.

The AI’s code, and what it printed:

Code the AI wrote 
corn |>
  mutate(says_irrigated = grepl("IRRIGATED", `Data item`)) |>
  count(Irrigated, says_irrigated)
# A tibble: 2 × 3
  Irrigated says_irrigated     n
      <dbl> <lgl>          <int>
1         0 FALSE             87
2         1 TRUE              74

Only two combinations appear: 0 with FALSE and 1 with TRUE. The two columns agree on every row, so a condition on Irrigated selects what you think it selects. If a row showed 1 with FALSE, the file would contradict itself, and you would ask whoever produced it before using either column.

Your turn: read the AI’s code

A student asked an AI for “the average yield of irrigated counties, and the five counties with the highest yields”, and got this:

corn |>
  filter(Irrigated == 0) |>

corn |>
  arrange(Yield) |>

  • Questions
  • Answers

A. Read each chain in words, saying “then” at each |>.

B. Which line gives the wrong average, without an error? How would you know, from what you looked at before asking?

C. The second chain has two problems. What are they?

D. Rewrite the request so the AI could not make these mistakes.

A. “Take corn, then keep the rows where Irrigated is 0, then compute the average yield.” “Take corn, then sort by yield, then show the first five rows.”

B. filter(Irrigated == 0) keeps the non-irrigated rows, so the average is 158.2, not 181.6. You know from count(corn, Irrigated) and the Data item check that 1 means irrigated.

C. arrange(Yield) sorts from the lowest yield up, so it shows the five lowest. And it starts again from all of corn, so non-irrigated rows are included; the request was about irrigated counties.

D. Say that Irrigated is 1 for irrigated, ask for the five irrigated rows with the highest yield, and ask it to print the values of Irrigated in the result and the first and last yields of the sorted table.
