An AI assistant can write the code that reads a file into R. It knows every function and every argument. What it cannot do is:

The concept

How reading code is written

A data file is a table saved on disk in some format. Reading it means a function opens the file and builds a table inside R (R calls it a data frame; this deck says table) that you give a name to. Whatever the format, and whichever function the AI picks, the code follows the same pattern.

  • The pattern
  • Every reader follows the pattern
  • Options
  • Variations you will see
table_name <- reader_function("path/to/file", option = value, ...)
Part What it is Required?
table_name <- The name the table will have inside R. <- stores the result under that name. Needed to keep the result
reader_function The function that understands the file’s format Yes
"path/to/file" Where the file is, always the first input Yes, the only required input
option = value Extra instructions about the layout and types No; each has a default

A real line that follows the pattern:

corn <- read_csv("corn_yields.csv")

On these slides the data files sit in the same folder as the slides, so a path is just the file name. In your own project, paths are built with here::here() (see Condition 1).

Readers differ in name and package, not in pattern. The shortest call to each is the path and nothing else:

Format Shortest call Package
csv read_csv("corn.csv") readr (tidyverse)
csv read.csv("corn.csv") built into R
Excel read_excel("corn.xlsx"), or read_xls(), read_xlsx() readxl
STATA read_dta("corn.dta") haven
R’s own readRDS("corn.rds") built into R

The help pages call the first input file for some readers and path for others. The name differs; its position, first, does not.

Everything after the path is optional and written as name = value. Each option you leave out takes its default, a value chosen by whoever wrote the function. Options you will see, grouped by what they tell the reader:

  • Which part of the file: sheet = "corn_yields_08" (Excel), skip = 2 (ignore lines above the column names)
  • What marks a missing value: na = c("", ".", "-999") (for read.csv(), na.strings =)
  • What type each column is: col_types = ..., for example to keep an ID column as text

Important

A default is a guess about your file. When the guess is wrong, R gives no error, and that is where the silent failures later in this deck come from. Knowing what your file looks like is how you know which options the AI must set.

AI-written code often wraps the same pattern in extra pieces. They change how the line looks, not what it does:

  • readr::read_csv(...): the package name, then ::, then the function. Uses the function without loading the whole package.
  • read_csv(here::here("data", "corn.csv")): the path is built by another function instead of typed out (see Condition 1).
  • path <- here::here("data", "corn.csv") on one line, then read_csv(path) on the next: the path is stored first and used later.
  • read_csv(...) |> some_other_step(): the table is passed straight on to a next step (|>) before it is stored.

What has to be true for an import to work

  • The four conditions
  • Failures with and without an error
  1. R can find the file. The path points at a file that exists.
  2. The reader matches the format. A csv reader for a csv file, an Excel reader for an Excel file.
  3. The reader understands the layout. Where the column names are, which sheet to read, what marks a missing value.
  4. Each column gets the right type. Numbers as numbers, text as text, IDs kept exactly as written.
  • If condition 1 or 2 fails, R stops with an error. Annoying, but you know something is wrong.
  • If condition 3 or 4 fails, R gives you a table with no error, and the table is wrong. This deck calls these silent failures.

Important

The silent failures are why checking matters. Code that runs is not the same as code that is right.

Condition 1: R can find the file

  • Paths
  • The project root and here()
  • Why AI gets this wrong

A path is the address of a file. There are two kinds:

  • Absolute path: starts at the top of the disk, for example "/Users/taro/Documents/class/corn_yields.csv". It works only on the computer it was written on, because nobody else has those folders.

  • Relative path: starts from the folder R is currently in (the working directory), for example "data/corn_yields.csv". It works only if R is in the folder you expected, and that folder changes:

  • At the Console: your project folder (if you opened an R Project, explained in the next tab)

  • Inside a .qmd file: the folder the .qmd is saved in

So "data/corn_yields.csv" can work at the Console and fail when a .qmd in analysis/ is rendered.

An R Project is a folder that RStudio marks with a .Rproj file; you open the project by opening that file. The top of that folder is the project root.

The safest path is one measured from the project root, whatever folder R is in. The here package does that: it finds the project root by looking for the .Rproj file. Recognise it when you see it:

corn <- read_csv(here::here("data", "corn_yields.csv"))

This reads data/corn_yields.csv inside your project, whichever subfolder your code is in and whoever’s computer it runs on. To check it is set up, run here::here() on its own at the Console: it should print your project folder.

The AI cannot see your folders, so it guesses the path. Its guesses tend to be one of these:

  • just the file name, assuming the file is in the working directory
  • an absolute path copied from an example, such as "C:/Users/yourname/..."
  • setwd(...) to change the working directory first

All three break as soon as the code runs somewhere else. Tell it where the file is (see “Asking AI” below).

If R says the file does not exist, send the AI the exact error message, the folder your .qmd is in, and where the file is inside your project.

Condition 2: the reader matches the format

The file extension (the part after the last dot) tells you the format. Tell the AI the extension and it will pick a reader from the list under “How reading code is written”. What you need to know is what each format keeps, because that decides what can go wrong:

Extension Format What the file keeps
.csv plain text, any software opens it Only text. Types are guessed on reading.
.xls, .xlsx Excel workbook Several sheets per file; a reader takes the first unless told otherwise
.dta STATA Types, and a description stored with each column
.rds R’s own format The exact R object, nothing guessed

Note

A csv file stores everything as text, so the reader has to guess each column’s type. That guessing is where conditions 3 and 4 go wrong.

Conditions 3 and 4: the silent failures

  • Lost leading zeros
  • Codes for missing values
  • The wrong sheet

County codes (FIPS) for Alabama start with 0. Here is a tiny csv, written straight into the code, and what the reader makes of it:

small_csv <- "fips,county,yield
01001,Autauga,150
01003,Baldwin,-999
31019,Buffalo,173"

small <- read_csv(I(small_csv), show_col_types = FALSE)
small$fips
[1] "01001" "01003" "31019"
read.csv(text = small_csv)$fips
[1]  1001  1003 31019

The two readers guessed differently about the same file. read_csv() kept 01001 as text. read.csv(), the built-in reader that AI assistants often write, decided the column was a number and turned 01001 into 1001. No error either way. Later, joining that table to another one by fips would quietly fail to match these counties.

The same file uses -999 to mean “no data”, a common convention. The reader does not know that:

mean(small$yield)
[1] -225.3333

An average yield of -225.3 bushels per acre, which is impossible. Again no error. The reader has to be told that -999 means missing.

corn_yields.xls has two sheets:

readxl::excel_sheets("corn_yields.xls")
[1] "corn_yields_08" "corn_yields_09"

A reader told nothing about sheets reads the first one only. If you wanted both years, you now have half the data, with no error.

Asking AI

Working with AI on your own research

This is the way of working with AI that you should take into your own research. Every exercise in this course uses it, so that it is a habit by the time your thesis needs it.

  1. You ask. Your request says what you want, what you know about the data, and which checks to print.
  2. The AI writes into a Quarto document (.qmd). Code goes into code chunks, with one plain-English sentence above each chunk saying what it does and why.
  3. You render the .qmd to HTML.
  4. You read the HTML and decide whether the work is right: the sentences, the code, and the check results side by side.

Why this matters for research, and why you judge the HTML rather than the chat window:

  • Rendering runs every chunk from the top in a fresh R session. If the HTML is right, the analysis is reproducible; nothing depends on something typed into the Console and forgotten.
  • The HTML is a record of what was done to the data and why, with each explanation next to its code and its result. You can reread it months later, and your advisor or a coauthor can review your analysis by reading it, without running anything.
  • The chat disappears; the .qmd and its HTML stay with your project.

Note

Every request that asks for code ends with the same few lines telling the AI to work this way. This deck calls them the closing instructions; the full text is under Recommended requests near the end.

Look at the file before you ask

  • Why
  • Raw first lines of a csv
  • Counting lines

You cannot describe a file you have not looked at, and you cannot check an import without knowing what the file holds. Two ways to look:

  • Open it: a csv in a text editor, an Excel file in Excel
  • Ask R to show the raw first lines, before any reader has guessed anything
readLines("corn_yields.csv", n = 3)
[1] "Year,State,FIPS,County_name,State_name,Commodity,Data item,Irrigated,Yield"                         
[2] "2008,31,31019,BUFFALO,NEBRASKA,CORN,\"CORN, GRAIN - YIELD, MEASURED IN BU / ACRE\",0,173"           
[3] "2008,31,31019,BUFFALO,NEBRASKA,CORN,\"CORN, GRAIN, IRRIGATED - YIELD, MEASURED IN BU / ACRE\",1,182"

From this you learn: the first line is column names, values are separated by commas, FIPS is a 5-digit code, one column name (Data item) has a space in it.

length(readLines("corn_yields.csv"))
[1] 162

162 lines, one of which is the column names. So a correct import has 161 rows. Write that number down before you import.

What to put in your request

The AI already knows the functions. Your request supplies what it cannot know, most of it from looking at the file:

  1. The file: its name, its format, and where it sits inside your project
  2. What is inside: the first few lines, the sheet names, and anything unusual (IDs with leading zeros, codes for missing values)
  3. What you want back: the name of the table, what one row is, and which type each key column should be
  4. Your project’s rules, if you have any beyond the closing instructions: for example, use the tidyverse
  5. Ask for checks: have it print the numbers you will check against (next section)
  6. The closing instructions: which .qmd and heading the code goes under, a sentence above each chunk, paths built with here::here(), checks printed as expected and got, and render to HTML

Using an agent in your editor or terminal?

An agent such as Claude Code can open the file and look for itself. Still write down what you expect (number of rows, types of key columns) before it runs, so you have something to compare against.

A weak request and a strong one

  • Weak
  • Strong
  • What came back
Read my corn data into R.

The AI has to guess the file name, its location, its format, its layout and what you want. A typical reply:

setwd("C:/Users/yourname/Documents")
corn <- read.csv("corn.csv")

It runs on nobody’s computer as written, and if you fix the path, it still guesses every type.

An example for a workbook with one sheet per year:

In my R project, the file data/corn_yields.xls is an Excel workbook with
two sheets, corn_yields_08 and corn_yields_09 (one per year). Each row is
one county, one year, and one irrigation status. I want both sheets
stacked into one table called corn, using the tidyverse, with FIPS kept
as text so leading zeros survive.

Then check the number of rows from each sheet (I expect 161 each), the
number of rows in corn (322), the type of every column, and the number
of missing values in each column (I expect none).

Put the code in my Quarto document analysis/import.qmd, under the
heading "Read the corn data", as R code chunks. Above each chunk, write
one plain-English sentence saying what it does and why. Build every path
with here::here(); no setwd(), no absolute paths. Print each check on
its own line as "name of check: expected X, got Y". Render the document
to HTML.

What the AI’s answer looks like in the rendered HTML: a sentence, then the chunk it describes. Read each sentence and check that the code under it does what the sentence says.

Read both sheets, keeping every column as text so that FIPS keeps its leading zeros.

library(readxl)
library(dplyr)

path <- here::here("data", "corn_yields.xls")
corn_08 <- read_excel(path, sheet = "corn_yields_08", col_types = "text")
corn_09 <- read_excel(path, sheet = "corn_yields_09", col_types = "text")

Stack the two sheets into one table, then turn Year and Yield back into numbers, since they were read as text.

corn <- bind_rows(corn_08, corn_09) |>
  mutate(Year = as.integer(Year), Yield = as.numeric(Yield))

Print the checks: rows per sheet and in total, the type of every column, and missing values per column.

cat("rows in 2008 sheet: expected 161, got", nrow(corn_08), "\n")
cat("rows in 2009 sheet: expected 161, got", nrow(corn_09), "\n")
cat("rows in corn: expected 322, got", nrow(corn), "\n")
sapply(corn, class)
cat("missing values: expected 0, got", sum(is.na(corn)), "\n")

Two things to notice. library() loads a package so its functions can be used, and bind_rows() stacks one table on top of another (you will meet it properly later in this chapter). And the type check would show that State and Irrigated are still text, because only Year and Yield were turned back into numbers. That is the type check doing its job: you would ask the AI to make those two numbers as well.

Checking the result

Checking: what to ask for, and why

  • The five checks
  • Asking for them
  • Reading the HTML

The AI can write the checking code. It cannot decide which checks your file needs, and it cannot know the right answers. Ask for these after every import:

Ask the AI to print Why What only you can supply
1 the number of rows and columns Rows go missing or appear when the wrong sheet is read or a title line is read as data the row count from looking at the file
2 the type of every column A wrong guess (an ID read as a number, a number read as text) gives no error which type each key column should be
3 the number of missing values in each column A missing-value code the reader was not told about, such as -999, is kept as a real value how the file marks missing values
4 the smallest and largest value of each numeric column Impossible values expose those codes, and unit mistakes what range is believable
5 the first row Shifted or merged columns show up at once the same row in the raw file

One sentence at the end of your request does it:

After reading the file, print: the number of rows and columns, the type of
every column, the number of missing values in each column, the smallest and
largest value of each numeric column, and the first row.

Better still, tell it what you expect, so the HTML says which checks passed:

I expect <number> rows, <number> columns, <ID columns> as text, <how many>
missing values, and <column> between <lowest> and <highest>. Print each
check on its own line as "name of check: expected X, got Y".

The second version only works if you looked at the file first. That part only you can do.

For corn_yields.csv, the student expected 161 rows (from counting lines), 9 columns, FIPS as text, no missing values, and yields between 100 and 250. The AI wrote the code; in the rendered HTML, you read each line:

Code the AI wrote 
cat(
  paste("rows: expected 161, got", nrow(corn)),
  paste("columns: expected 9, got", ncol(corn)),
  paste("type of FIPS: expected character, got", class(corn$FIPS)),
  paste("missing values: expected 0, got", sum(is.na(corn))),
  paste("Yield range: expected 100 to 250, got", min(corn$Yield), "to", max(corn$Yield)),
  paste("first row:", paste(unlist(corn[1, ]), collapse = ", ")),
  sep = "\n"
)
rows: expected 161, got 161
columns: expected 9, got 9
type of FIPS: expected character, got numeric
missing values: expected 0, got 0
Yield range: expected 100 to 250, got 103 to 204
first row: 2008, 31, 31019, BUFFALO, NEBRASKA, CORN, CORN, GRAIN - YIELD, MEASURED IN BU / ACRE, 0, 173
  • Rows, columns, missing values and the yield range match.
  • The first row matches the second line of the file (shown under “Look at the file before you ask”).
  • FIPS came back as a number, not the text you expected. In this file every code starts with 31, so nothing was lost, but the check fails, and you would ask the AI to read FIPS as text.

Checks that come from knowing the data

The five checks apply to any file. The most useful checks come from what you know about this data, and no AI will think of them for you.

In corn_yields.csv, most counties have two rows: one for irrigated corn and one for non-irrigated corn. Irrigated corn gets water that rain-fed corn does not, so in each county the irrigated yield should be the higher one. So ask:

Using the table corn, for each county with one irrigated and one
non-irrigated row, check whether the irrigated yield is higher. Print
how many counties pass and how many fail.

The AI’s code, and what it printed:

Code the AI wrote 
corn |>
  group_by(FIPS) |>
  filter(n() == 2, n_distinct(Irrigated) == 2) |>
  summarise(irrigated_higher = Yield[Irrigated == 1] > Yield[Irrigated == 0]) |>
  count(irrigated_higher)
# A tibble: 1 × 2
  irrigated_higher     n
  <lgl>            <int>
1 TRUE                70

All 70 counties pass. A row count or a type check could never have tested this; only what you know about corn could.

When a check like this fails, the code is usually not the problem: the file is. Stop, and ask whoever produced the file before you analyse it.

Exporting

How writing code is written

Writing (exporting) is reading in reverse: a function takes a table from R and saves it as a file. Again, every writer follows the same pattern.

  • The pattern
  • Every writer follows the pattern
  • A default that surprises
  • Choosing a format
writer_function(table_name, "path/to/file", option = value, ...)
Part What it is Required?
writer_function The function that writes this format Yes
table_name The table to save, always the first input Yes
"path/to/file" Where to save it, always the second input Yes
option = value Extra instructions, such as how to write missing values No; each has a default

Two differences from reading:

  • There is no table_name <- in front. The result is a file on disk, not a new table in R.
  • If a file already exists at that path, it is replaced without asking. Writing to the same path as your raw data destroys the raw data.
Format Shortest call Package
csv write_csv(corn, "corn.csv") readr (tidyverse)
csv write.csv(corn, "corn.csv") built into R
Excel write_xlsx(corn, "corn.xlsx") writexl
STATA write_dta(corn, "corn.dta") haven
R’s own saveRDS(corn, "corn.rds") built into R

The same variations as for reading appear here too: readr::write_csv(...), and the path built with here::here(...).

Defaults matter when writing too. The built-in write.csv() adds a column of row numbers by default. Read the file back, and that column returns as an extra column:

tmp <- file.path(tempdir(), "corn_base.csv")
write.csv(corn, tmp)
names(read.csv(tmp))
 [1] "X"           "Year"        "State"       "FIPS"        "County_name"
 [6] "State_name"  "Commodity"   "Data.item"   "Irrigated"   "Yield"

The extra first column, X, holds 1, 2, 3, and so on. Adding row.names = FALSE prevents it; write_csv() never adds it. When the AI writes write.csv(), check for that option.

Notice also that Data item came back as Data.item. That one is a default of the reader: read.csv() replaces spaces in column names with dots, and read_csv() does not.

The decision that is yours is the format, and it depends on who reads the file next and what has to survive:

Format Choose it when What is lost
csv anyone, in any software, must be able to read it every type: dates, factors (columns of categories) and text IDs come back as guesses
rds you, in R, will read it in the next step of the project nothing, but only R can open it
dta a collaborator uses STATA some R-only types

A reasonable default

Keep raw data as you received it. Save intermediate results as rds, so types survive from one script to the next.

Checking an export: the round trip

Why: a file can quietly keep less than you saved. The only way to know what it kept is to read it back.

What to ask: “Save the table, read it back, and compare it with the original.” Here Irrigated was first made a factor, then saved as csv and as rds:

Code the AI wrote 
corn_f <- mutate(corn, Irrigated = factor(Irrigated, labels = c("no", "yes")))

csv_file <- file.path(tempdir(), "corn.csv")
rds_file <- file.path(tempdir(), "corn.rds")
write_csv(corn_f, csv_file)
saveRDS(corn_f, rds_file)

c(
  from_csv = class(read_csv(csv_file, show_col_types = FALSE)$Irrigated),
  from_rds = class(readRDS(rds_file)$Irrigated)
)
   from_csv    from_rds 
"character"    "factor"

The csv gave back text: the factor was lost. The rds gave back the factor.
