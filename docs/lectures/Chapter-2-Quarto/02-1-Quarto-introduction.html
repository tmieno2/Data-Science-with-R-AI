The concept

Why research is written in a Quarto document

  • The problem
  • What Quarto does

The usual way of reporting an analysis is to run code in one place and copy the results into another: a Word file, an email, a chat window. Three things go wrong:

  • Numbers drift. The data changes, the code is rerun, and the number typed into the report is not updated.
  • Nobody can see how a number was made. The report shows the result, not the steps that led to it.
  • The steps get lost. Code run once in a terminal or a chat and never saved cannot be run again, by you or anyone else.

A Quarto document is one plain-text file that holds both the sentences and the code. Rendering it (the agent runs the render, or you click Preview in VS Code) runs the code and writes an HTML page in which each piece of code sits next to its result and the sentence that explains it.

  • The .qmd file is the source: you, or the AI, edit it.
  • The .html file is the output: you read it, and you send it to whoever needs to see the work.

These slides are themselves a Quarto document, rendered to a slide format instead of a page.

Note

Quarto can also render to slides, websites, Word files and PDF articles. Lectures 02-2 to 02-4 cover those. This lecture uses HTML pages throughout.

What you type What you get

+ item or - item a bullet list item

**text** bold

`text` code style, inside a sentence

The headings matter beyond looks: they are how you tell the AI where to put its code (“under the heading …”).

A short report that follows the pattern. In the next tab you render it and see what rendering makes of it.

---
title: "Field yields"
format: html
---

## Average yield

Make a table of four fields, written straight into the code.

```{r}
#| label: make-fields
fields <- data.frame(
  field = c("North", "South", "East", "West"),
  acres = c(40, 80, 35, 120),
  yield = c(182, 201, 175, 196)
)
```

Compute the average yield across the four fields.

```{r}
#| label: average-yield
mean(fields$yield)
```

The average yield is `r mean(fields$yield)` bushels per acre.

What a code chunk can put on the page

When a document is rendered, each chunk’s result appears in the HTML right below its code. For every chunk you decide what the reader sees: the code, the result, both, or neither.

  • A printed result
  • A table
  • A figure
  • What you can choose
  • Code folded
  • Result only
  • Nothing shown

Whatever R prints appears under the code. Below, the first box is the code; the box under it is what R printed when the document was rendered.

mean(fields$yield)
[1] 188.5

The [1] at the start is R’s way of numbering the printed values; this result is a single number.

Printing a table puts its rows in the page:

fields
  field acres yield
1 North    40   182
2 South    80   201
3  East    35   175
4  West   120   196

This is R’s plain printout. The AI can also turn a table into a formatted one, with column headings and units (Chapter 8).

A chunk that makes a figure puts the figure in the page:

ggplot(fields, aes(x = field, y = yield)) +
  geom_col() +
  labs(x = NULL, y = "Yield (bushels per acre)")

For each chunk:

Both shown shown Most steps of an analysis nothing: the default
The result, with the code one click away behind a button shown A report for readers who may want to check the code code-fold: true
The result only not shown shown A figure or table for readers who do not read code echo: false

What rendering does

  • The four steps
  • Only what is in the document exists
  • Order matters
  • The folder

When you click Render, Quarto:

  1. Starts a new R session (a fresh, empty R, separate from any R the agent or you already had running)
  2. Runs every chunk, in order, from the top, with the folder that holds the .qmd as the working directory (the folder R treats as “here”)
  3. Puts the text, the code and the results together
  4. Writes the HTML file next to the .qmd, and opens it

If any chunk stops with an error, the render stops there and no new HTML is written. The HTML from the last successful render stays where it was, so after a failed render the page you open is out of date. Check the render’s message before reading the page.

The new R session in step 1 knows nothing about any other R session. A table made by code run outside the document (by the agent in its own terminal, or by you at an R Console, the window where R runs typed lines one at a time), or a package loaded there, does not exist for the render.

Suppose the agent ran farms <- read_csv("farms.csv") in its terminal to look at the data, and the document has a chunk labelled count-farms with nrow(farms) in it. Run in that same session, the chunk works, because farms exists there. Rendering stops with:

Error:
! object 'farms' not found
Quitting from report.qmd:6-9 [count-farms]

The fix is never to run more code outside the document. It is to put the line that makes farms into a chunk above count-farms.

Step 2 runs the chunks once, from top to bottom. A chunk can use only what the chunks above it made.

While you work, you can run chunks by hand in any order, so a document can seem to work when it does not: a chunk near the top that uses a table made further down works if you happened to run the lower chunk first. The render does not; it stops at the first chunk that needs something not yet made.

During the render, R’s working directory is the folder the .qmd is saved in, not necessarily your project folder (the folder you open in VS Code; lecture 03-1). A path such as "data/farms.csv" is looked up starting from that folder.

So a path that works outside the document can fail inside a .qmd saved in a subfolder. The fix is here::here(), which builds a path starting from the project folder wherever the .qmd is. Lecture 03-1 explains paths in full; for now, recognise here::here("data", "farms.csv") as “the file farms.csv in the data folder of this project”.

Why a document that renders is reproducible

Reproducible means that someone else, or you a year from now, can run the same steps on the same data and get the same results.

Rendering tests that every time: it starts from nothing and builds every result from the document alone. So if a document renders:

  • every step is written down in it, in the order it runs
  • nothing depends on code run outside the document and forgotten
  • every number computed in it comes from the data, through the code you can read

What rendering does not tell you

A document that renders is complete, not necessarily right. The code can run and still do the wrong thing, a sentence can describe something the code does not do, and a chunk option can keep a step out of view. That is why you read the HTML (see “Checking the result”).

A cached chunk (next slide) is the one exception to “starts from nothing”: it can show a result from an earlier render.

Caching: a shorter render for slow chunks

  • The problem
  • What caching is
  • When it shows old results
  • Making it safe
  • Another way: save the result to a file
  • Asking the AI
  • Checking

Every render runs every chunk again, from the top (slide “What rendering does”). Most chunks take less than a second. Some take minutes: reading a very large file, fitting a model to millions of rows, running a simulation.

In a document with such a chunk, every render takes minutes, even one that only fixes a typo in a sentence. That cost adds up fast when the agent works for you, because it renders after every change it makes.

Caching a chunk means saving what it made, so later renders can load it instead of running the chunk again. You switch it on per chunk with the option cache: true:

```{r}
#| label: fit-model
#| cache: true
model <- lm(yield ~ nitrogen, data = trials)
```
  • First render: the chunk runs as usual. Everything it made (here, model) and everything it printed is saved to a folder next to the .qmd, named after the document plus _cache (for report.qmd, the folder report_cache).
  • Later renders: the chunk does not run. The saved results are loaded from that folder, which takes a moment instead of minutes.

The HTML looks the same either way. Nothing on the page says whether a result was computed now or loaded from an earlier render.

Before loading the saved results, the render checks one thing: has the chunk itself changed (its code, or one of its options that affects results)? If yes, it runs the chunk again and saves the new results. If no, it loads the saved ones.

It does not look outside the chunk. So it loads the old results, with no warning, when:

  • the data file the chunk reads has changed, for example a corrected or extended version of trials.csv
  • a chunk above it has changed a table it uses, for example a chunk that drops bad rows now drops different ones

We tested this: a cached chunk printed the sum of a column in a data file. After 100 was added to the file, the next render still printed the old sum.

This is what makes caching risky: the page looks right and is out of date.

Two chunk options tell the render what else to check, and one command clears everything:

What What it does
cache-extra: !expr tools::md5sum(here::here("data", "trials.csv")) Run the chunk again when the contents of this file change. tools::md5sum() turns a file’s contents into a short code; any change to the file changes the code
dependson: "clean-trials" Run the chunk again whenever the chunk labelled clean-trials runs again. That chunk must be cached too
quarto render report.qmd --cache-refresh Run every cached chunk again this once, and save new results. Deleting the _cache folder does the same

So a cached chunk is safe when every file it reads is named in cache-extra, and every cached chunk whose tables it uses is named in dependson.

For a very slow step, or a download, there is a plainer way: one step runs once and saves its result to a file (for example an .rds file, R’s format for saving one object), and the document reads that file.

  • The saved file is visible in your project folder, and you decide when to make it again.
  • The document renders fast, because reading a saved result is quick.

Caching suits a chunk inside the document that takes seconds to minutes. Saving to a file suits a step that takes hours, or one that downloads data. Chapter 6 shows how a project is split into such steps.

The agent can see that a render was slow, and it may switch caching on by itself. What it cannot know:

  • which data files may still change: a file you will receive again, correct, or extend
  • whether this is the final render, the one whose numbers go into your paper

So when you ask for caching, name the files each slow chunk reads, and ask for cache-extra on them (request “Speed up a slow chunk” under “Requests you can copy”). Before the final render, ask for a render with --cache-refresh.

  1. It saves time. Render twice. The second render should be much faster, and a _cache folder should be next to the .qmd.
  2. It is safe. Open the .qmd. For every chunk with cache: true: is every file it reads named in cache-extra, and every cached chunk it uses named in dependson?
  3. The numbers are current. Render once with --cache-refresh. Every number in the HTML should be the same as in the render before. A number that changed was out of date.

Reading a .qmd file

How the YAML header is written

  • The pattern
  • Settings you will see

Every line of the header is a setting, written as a name, a colon and a value:

---
name: value
group:
  name: value
---
Part What it is
name: value One setting. Text values with spaces or colons go in quotes: title: "Yield: a first look"
A name with nothing after the colon A group. The settings that belong to it are on the lines below, indented further
Indentation Spaces, never tabs. How far a line is indented says which group it belongs to 
---
title: "Field yields"
author: "Your Name"
date: today
format:
  html:
    toc: true
    embed-resources: true
    code-fold: true
execute:
  warning: false
---
Setting What it does
title, author Printed at the top of the page
date: today Prints the date of the render
format: html Produce an HTML page. Settings for that format go in the group under html:
toc: true Add a table of contents built from the headings
embed-resources: true Pack figures and styling into the one HTML file, so it can be sent on its own (see “Checking the result”)
code-fold: true Hide each chunk’s code behind a “Code” button the reader can click
execute: Chunk options that apply to every chunk; here, hide warnings everywhere

toc belongs to html, so it must be indented further than html:. Here it is not:

---
title: "Field yields"
format:
  html:
  toc: true
---

Quarto refuses to render, names the line, and prints Render failed due to invalid YAML. When the AI changes a header and the render then fails at once, the header is the first place to look.

How a code chunk is written

  • The pattern
  • Variations you will see
```{r}
#| label: name-of-chunk
#| option: value
R code
```
Part What it is Required?
```{r} and ``` The start and end of the chunk; r says the code is R Yes
#| label: ... A name for the chunk: unique in the document, no spaces No, but an error message then names the chunk by its label
#| option: value One chunk option per line, right below the first line, with no blank line in between. The options are the choices on the slide “What a code chunk can put on the page” No; each has a default
R code Runs when the document is rendered Yes
  • execute: in the YAML header, with options under it: sets those options for every chunk. An option written in a chunk overrides it for that chunk.
  • #| fig-cap: "...": a caption under a figure.
  • #| error: true: the render continues past an error in this chunk and prints the error in the page, instead of stopping.
  • #| echo: false and {r, echo = FALSE} (options inside the braces): the second is an older way of writing the same thing. Both work.
  • #| label: fig-yield with #| fig-cap: "...": a label that starts with fig- makes a numbered figure that the text can refer to (lecture 02-4).
  • A chunk with only library(...) lines and include: false at the top of the document: a setup chunk. It loads packages without filling the page with them.

How inline R is written

  • The pattern
  • Why it matters
  • Variations you will see

Inside a sentence, a backtick, the letter r, a space, an R expression and a closing backtick:

The average yield is `r mean(fields$yield)` bushels per acre.

When the document is rendered, the expression is run and its result replaces it. The reader of the HTML sees only the number:

The average yield is 188.5 bushels per acre.

It runs in the same R session as the chunks, so it can use anything made by a chunk above it.

A number typed into a sentence is a copy, made once. A number written with inline R is computed at every render, so it always matches the data and the code.

If someone adds a fifth field to fields and renders again, the sentence changes by itself:

fields_5 <- rbind(fields, data.frame(field = "Creek", acres = 25, yield = 150))
mean(fields_5$yield)
[1] 180.8

A typed “188.5 bushels per acre” would now be wrong, and nothing would say so.

  • `r round(mean(fields$yield), 1)`: rounded inside the sentence
  • A value computed in a chunk, given a name, and only the name used inline: `r avg_yield`. Long calculations belong in a chunk, not in a sentence.
  • `{r} mean(fields$yield)`: a newer way of writing the same thing. Both work.

When a render fails

  • Read the message
  • Errors you will meet
  • What to send the AI

Quarto prints the error in the terminal where the render ran: the agent’s, when the agent rendered (it shows the lines in its reply), or the Terminal panel at the bottom of VS Code, when you clicked Preview. Read the last lines first:

Error:
! object 'farms' not found
Quitting from report.qmd:6-9 [count-farms]
  • The line starting with ! is R’s own error.
  • Quitting from names the file, the lines, and the chunk’s label in square brackets.
The error says What it usually means
object '...' not found The table or value is made outside the document or further down it, not in a chunk above this one
could not find function "..." The package is loaded outside the document but not in it, or the name is misspelled
cannot open file '...' or does not exist The path is wrong from the .qmd’s folder (Lecture 03-1)
Render failed due to invalid YAML A mistake in the header: usually indentation, or a missing colon

If the agent rendered, it saw the error and will usually try a fix. If you rendered, the agent did not see it. Send it:

  1. the error lines, copied exactly
  2. the chunk the error names
  3. the folder the .qmd is in, if the error is about a file
  4. that the fix must go into the document, not be run outside it, which would hide the problem until the next render

Either way, have it render again. “Fixed” means the document renders, not that the AI says it is fixed.

Asking AI

Working with AI on your own research

This is the way of working with AI that you should take into your own research. Every exercise in this course uses it, so that it is a habit by the time your thesis needs it.

  1. You ask. Your request says what you want, what you know about the data, and which checks to print.
  2. The AI writes into a Quarto document (.qmd). Code goes into code chunks, with one plain-English sentence above each chunk saying what it does and why.
  3. The AI renders the .qmd to HTML.
  4. You read the HTML and decide whether the work is right: the sentences, the code, and the check results side by side.

Why this matters for research, and why you judge the HTML rather than the chat window:

  • Rendering runs every chunk from the top in a fresh R session. If the HTML is right, the analysis is reproducible; nothing depends on code run outside the document and forgotten.
  • The HTML is a record of what was done to the data and why, with each explanation next to its code and its result. You can reread it months later, and your advisor or a coauthor can review your analysis by reading it, without running anything.
  • The chat disappears; the .qmd and its HTML stay with your project.

Note

Every request that asks for code ends with the same few lines telling the AI to work this way. This deck calls them the closing instructions; the full text is under Recommended requests near the end.

What to put in your request

The AI can write any chunk and any header. What it cannot know is how your document is organised and who reads it. Your request supplies:

  1. Where the code goes: which .qmd, and under which heading
  2. What the reader should see: code shown, code folded behind a button, or only the result. Only setup chunks (loading packages) should be hidden completely.
  3. Which numbers go into sentences: ask for them as inline R, never typed
  4. The checks: what to print so the HTML shows whether the step worked
  5. The closing instructions: which .qmd and heading, a sentence above each chunk, paths built with here::here(), checks printed as expected and got, and render to HTML

Chat assistant or agent?

A chat assistant cannot open or render your files: paste its chunks into your .qmd under the right heading and render yourself. An agent in your editor or terminal, such as Claude Code, can edit and render the file itself. Either way, you read the HTML.

A weak request and a strong one

  • Strong

What is the average yield of my fields?

A typical reply is a number in the chat window, or code it ran outside your document. Either way, the number is not in your document, no one can see how it was made, and the next time the data changes, nothing updates it.

and write one sentence reporting it, with the number written as inline

Put the code in my Quarto document analysis/report.qmd, under the
heading "Average yield", as R code chunks. Above each chunk, write one
plain-English sentence saying what it does and why. Build every path
with here::here(); no setwd(), no absolute paths. Print each check on
its own line as "name of check: expected X, got Y". Render the document

What the AI’s answer looks like in the rendered HTML: a sentence, then the chunk it describes, then the sentence with the number.

Check that the table has the four fields expected, then compute the average yield.

cat("number of fields: expected 4, got", nrow(fields), "\n")
number of fields: expected 4, got 4 
avg_yield <- round(mean(fields$yield), 1)

The average yield across the fields is 188.5 bushels per acre.

In the .qmd, that last sentence reads `r avg_yield`, not a typed number. Opening the .qmd to confirm it is part of checking: the HTML looks the same either way.

Checking the result

What to check in the HTML, and why

  • The checks
  • What the HTML can hide
  • Sending the HTML

The AI cannot see the rendered page the way your reader does. Check these every time:

Check Why What only you can supply
1 It renders A render starts from nothing, so it proves nothing depends on code run outside the document Doing it, and reading the render’s message
2 Every chunk has a sentence above it, and the code does what the sentence says The sentence is what a reader trusts; a wrong one misleads Reading both
3 Every “expected X, got Y” line matches The checks are where a silent mistake shows up The expected values, from knowing your data
4 No step that changes the data is hidden A hidden chunk changes the results without a trace in the HTML Opening the .qmd and looking at the chunk options
5 Every number in a sentence agrees with the result above it, and is inline R in the .qmd A typed number goes stale without warning Comparing them

The HTML shows what the chunk options let it show. Here, a chunk with include: false dropped the smallest field before the average was computed. The reader sees only this:

Compute the average yield across the fields.

mean(fields_shown$yield)
[1] 193

Nothing on the page says that a field was dropped. Only the .qmd does, or a check of the number of fields printed in the HTML (expected 4, got 3). This is why check 4 means opening the .qmd, and why every chunk except the setup chunk should be shown or folded, never hidden (an article may also hide a chunk that only prints checks, lecture 02-4).

By default, rendering report.qmd writes report.html and a folder report_files/ holding its figures and styling. The HTML only points at that folder.

  • Send report.html on its own, and the reader sees it without its figures and styling.
  • With embed-resources: true under html: in the header, everything is packed into the one HTML file.

To check: move only the .html file to another folder, open it there, and confirm the figures are still in it.
