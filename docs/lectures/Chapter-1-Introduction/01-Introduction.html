01-1: Introduction to R

How this lecture works

What you will and will not learn today

  • The plan
  • Directions

An AI assistant can write R code. What it cannot do is tell you whether that code did what you needed. To judge that, you have to be able to read R code: say what each line does, even if you could not have written it yourself.

This first lecture gives you the foundation for reading code. Every line of R you will see in this course is built from three things:

  1. Objects: named things that hold values, created with <-
  2. Functions: commands that take inputs and give back a result
  3. Packages: collections of functions written by other people, which you install and then load

You will not learn to write these from memory. You will learn to recognise them, so that when an AI hands you code, you can follow it line by line.

  • Install R, then RStudio (see “Installing them” under “R and RStudio” below)
  • Install the packages tidyverse, rmarkdown and here, at the Console: install.packages(c("tidyverse", "rmarkdown", "here")). Do this before class; it can take several minutes. What packages are, and why installing happens once, is on the slide “Packages: installing and loading”
  • Have an AI assistant available: a chat assistant in your browser, or an agent such as Claude Code in your editor or terminal
  • To move around these slides: click the three stacked horizontal lines in the bottom-left corner for the table of contents, or press the o key to see every slide at once

The code on these slides was run when the slides were made, and its output is shown under it. To try it yourself, copy it into RStudio.

Why the course works this way

  • R does exactly what the code says
  • Your job, and the AI’s
  • What the course is for

R runs each line exactly as written. Given a line it cannot make sense of, it stops and prints an error. Given a line it can run, it follows its own rules, even when the result is not what you meant.

An AI assistant is the opposite. Given a request with gaps, it fills them in with guesses: where your files are, what your data holds, what you wanted the result for. It writes code that runs, and the guesses are inside it.

So the risk has moved. Code that does not run is easy to spot. Code that runs and does the wrong thing is not, and that is what you have to catch.

The AI does You do
Knows every function and every input Understand the step: what it is for, and what has to be true for it to work (the concept)
Writes the code Recognise what each line does (reading code)
Fills gaps with guesses Tell it what it cannot know: your files, your data, your purpose (asking)
Reports that the code ran Decide whether the result is right, using checks whose answer you know in advance (checking)

Every lecture in this course is organised around those four parts.

By the end, you should be able to carry out your own research in R with an AI assistant writing the code: get data in, reshape it, make figures and tables, report the results, and work with maps.

The AI will write that code into a Quarto document (a .qmd file: plain text with R code in it). Rendering the document runs its code from the top and makes a web page showing the code and its results. Chapter 2 teaches Quarto.

R and RStudio

R and RStudio

  • What they are
  • Installing them
  • The four panes
  • Running code

R is a programming language for statistics and data, and the program that runs code written in it.

  • Free and open source, and widely used in universities and in industry
  • Started as software for statistics, designed by statisticians
  • Grows through its users: new statistical methods often appear first as R packages written by the people who developed the method, and R also handles maps and large datasets

RStudio is a separate program that you work in. It sends your code to R and shows you the results, your files, your figures and the help pages in one window. R’s own window is very basic, so almost everyone uses R through RStudio.

Install both, R first, then RStudio, because RStudio looks for an existing R installation when it starts.

  • R
  • RStudio

It worked if RStudio opens and the lower-left pane shows a line starting with R version followed by a >.

Where Pane What it is for
Upper left Script or document Code you want to keep, saved in a file
Lower left Console Where R runs code. Type a line after > and press Enter
Upper right Environment Lists the objects R is currently holding
Lower right Files, Plots, Packages, Help Your folders, figures, installed packages and help pages

Appearance and pane layout can be changed under Tools, Global Options.

  • At the Console: type a line and press Enter. R prints the result.
  • In a file: put the cursor on a line, or select several lines, and press Command + Enter (Mac) or Ctrl + Enter (Windows). RStudio sends them to the Console.

Anything after # on a line is a comment: R ignores it. Comments explain the code to people.

# this whole line is a comment
2 + 3 # a comment can follow code on the same line
[1] 5

The [1] at the start of the output is not part of the result. It says the line of output starts with the first value.

Reading code

The three building blocks in one line

Here is a typical line of R, of the kind an AI writes all the time:

average_yield <- mean(yields, na.rm = TRUE)
Piece What it is Slide
average_yield The name of a new object, which will hold the result Objects and <-
<- Stores the result of the right-hand side under that name Objects and <-
mean A function: it computes an average Functions and their inputs
yields An existing object, the first input to the function Functions and their inputs
na.rm = TRUE A named input: an option that changes what the function does Functions and their inputs

mean() is built into R. Many functions are not: they come from a package, which has to be installed and loaded first (slide “Packages”).

The rest of this section takes the pieces one at a time. By the end of it, you should be able to read the line above out loud: “compute the average of yields, leaving out missing values, and store it as average_yield”.

Objects and <-

  • The pattern
  • Printing an object
  • Overwriting
  • <- versus =

An object is a named thing R holds in memory: a number, some text, a table of data, a fitted model. Every object is made by the same pattern:

name <- value
Part What it is
name The name you will use to refer to the object later
<- “Store the right-hand side under this name”. Read it as “gets”: a gets 1
value Anything that produces a result: a number, text, or a whole calculation

R works out the right-hand side first, then stores the result. So d <- 1 == 2 stores FALSE, the answer to “is 1 equal to 2?”, not the question.

a <- 1
b <- "R rocks"
d <- 1 == 2

These three objects now appear in RStudio’s Environment pane.

Running an object’s name on its own prints what it holds. This is the simplest check there is: did the object get the value you expected?

a
[1] 1
b
[1] "R rocks"
d
[1] FALSE

Storing under a name that already exists replaces the old object, without a warning:

a <- 3
a <- 1
a
[1] 1

Outside a function, name = value does the same as name <- value. You will see both in AI-written code; this course uses <-.

Inside a function’s parentheses, = means something different: it sets one of the function’s inputs. In mean(yields, na.rm = TRUE), na.rm = TRUE does not create an object called na.rm. It tells mean() to leave out missing values (slide “Functions and their inputs”).

Values and their types

  • The types
  • Operators
  • Missing values: NA

Every value has a type. The type decides what R can do with it.

Type Examples What it is
numeric 1, 1.3, -999 A number, whole or with decimals
character "Nebraska", "31001" Text, always written inside quotation marks
logical TRUE, FALSE The answer to a yes-or-no question

You will also see integer (a whole number written with an L, such as 3L); it behaves like numeric.

Quotation marks matter: "31001" is text, 31001 is a number. You cannot do arithmetic on text:

"5" + 1
Error in "5" + 1: non-numeric argument to binary operator

Arithmetic and comparisons follow the usual signs, with a few that may be new:

Operator Meaning Example Result
+ - * / add, subtract, multiply, divide 6 / 4 1.5
^ to the power of 2^3 8
==, != is equal to, is not equal to 5 == 4 FALSE
>, <, >=, <= greater than, less than, and so on 5 > 4 TRUE

A comparison gives back a logical value. == (two equals signs) asks a question; a single = sets a value. Comparisons are how rows are kept or dropped from a table later in the course.

NA means “this value is missing”. It is not zero, and it is not the text "NA".

yields
[1] 150 162  NA 171
is.na(yields)
[1] FALSE FALSE  TRUE FALSE

is.na() asks of each value “is it missing?”. The third one is.

Most calculations that include a missing value give NA, because the true answer is unknown:

mean(yields)
[1] NA

How to get the average of the values that are there is on the slide “Functions and their inputs”, tab “Defaults”.

Vectors and tables

  • Vectors
  • One type per vector
  • Tables
  • Other objects you will see
  • What kind of object is it?

A vector is a sequence of values, all of the same type. c() (short for “combine”) makes one:

v <- c(4, 3, 5, 9, 1)
v
[1] 4 3 5 9 1

Arithmetic on vectors works element by element: the first value with the first, the second with the second, and so on.

v * 2
[1]  8  6 10 18  2
v + c(10, 20, 30, 40, 50)
[1] 14 23 35 49 51

R code rarely needs a loop to do the same thing to every value; this is why.

A vector can hold only one type. Mix types, and R converts everything to the type that can hold all of them, without an error:

mixed <- c(4, 3, "5", 9, 1)
mixed
[1] "4" "3" "5" "9" "1"

Every value is now text (note the quotation marks). One text value turned the whole vector into text. When a column of numbers arrives in your analysis as text, this is usually why, and arithmetic on it will then fail or give NA.

A table holds data in rows and columns. Each column is a vector, so each column has one type, but different columns can have different types. All columns have the same length. R calls a table a data frame; this course says table.

yield_data <- data.frame(
  nitrogen = c(200, 180, 300),
  yield = c(240, 220, 230),
  state = c("Kansas", "Nebraska", "Iowa")
)
yield_data
  nitrogen yield    state
1      200   240   Kansas
2      180   220 Nebraska
3      300   230     Iowa

Inside data.frame(), each name = c(...) makes one column. Values in the same position make one row.

You will also see tibble and data.table. They are tables too, with some extra conveniences; read them as tables.

  • list: holds any mix of objects, each of any type and length. Results of a statistical model usually come back as a list.
  • matrix: values of one type in rows and columns, used for linear algebra. You will rarely meet one in this course.
a_list <- list(numbers = c(10, 20), state = "Iowa", data = yield_data)
names(a_list)
[1] "numbers" "state"   "data"

Many surprises in R come from an object not being what you thought: a column of text instead of numbers, a vector instead of a table. Three functions tell you:

class(yield_data)
[1] "data.frame"
class(mixed)
[1] "character"
str(yield_data)
'data.frame':   3 obs. of  3 variables:
 $ nitrogen: num  200 180 300
 $ yield   : num  240 220 230
 $ state   : chr  "Kansas" "Nebraska" "Iowa"

class() gives the kind of object; for a vector, the type of its values. str() (structure) gives the size and the type of every column: here 3 rows (“obs.”) and 3 columns (“variables”), with num for numeric and chr for character. In RStudio, View(yield_data) opens a table in a spreadsheet-style viewer.

Pulling parts out of an object

AI-written code constantly takes one column, some rows or one value out of an object. Whatever the object, it is done with brackets or $, in one of these patterns:

Pattern Gives Example Result
vector[position] values at those positions v[2] 3
table$column one column, as a vector yield_data$yield 240 220 230
table[condition, ] the rows where the condition is TRUE; the empty place after the comma means “all columns” yield_data[yield_data$yield > 225, ] the 2 rows with yield above 225
list[[position]] or list$name one element of a list a_list$state Iowa

Positions count from 1, not 0. table$column is the one you will see most often: mean(yield_data$yield) reads “the average of the yield column of yield_data”.

mean(yield_data$yield)
[1] 230

The condition is itself a comparison that gives one TRUE or FALSE per row, and the rows marked TRUE are kept:

yield_data$yield > 225
[1]  TRUE FALSE  TRUE
yield_data[yield_data$yield > 225, ]
  nitrogen yield  state
1      200   240 Kansas
3      300   230   Iowa

Functions and their inputs

  • The pattern
  • Functions you will see
  • Defaults
  • Variations you will see

A function takes inputs, does something with them, and gives back a result. Every function call follows the same pattern:

result <- function_name(first_input, name = value, ...)
Part What it is Required?
result <- Stores what the function gives back No; without it, the result is printed and then gone
function_name What to do Yes
( ) Holds the inputs, separated by commas. R calls the inputs arguments Yes, even if empty
first_input Usually the data to work on, matched by its position Usually
name = value An option, matched by its name No; each has a default

A real call:

round(3.14159, digits = 2)
[1] 3.14

The first input, 3.14159, is the number to round. digits = 2 is an option. Leave it out and round() uses its default, 0 digits: round(3.14159) gives 3.

All of these follow the pattern. You do not need to remember them; you need to recognise the pattern when you see them.

Function What it gives back Example Result
mean(), sum(), min(), max() one number summarising a vector sum(v) 22
length() how many values a vector has length(v) 5
nrow(), ncol() rows or columns of a table nrow(yield_data) 3
round() rounded numbers round(2.567, digits = 1) 2.6
seq() a sequence of numbers seq(0, 10, by = 5) 0 5 10
rep() repeated values rep(10, times = 3) 10 10 10
is.na() TRUE where a value is missing is.na(c(1, NA)) FALSE TRUE
class(), str() what kind of object something is class(v) numeric

Every option has a default: the value it takes when you do not set it, chosen by whoever wrote the function. mean() has an option na.rm (remove NAs) whose default is FALSE. That is why the average above came back NA:

mean(yields)
[1] NA
mean(yields, na.rm = TRUE)
[1] 161

With na.rm = TRUE, the average is of the 3 values that are there: (150 + 162 + 171) / 3 = 161.

Important

AI-written code often adds na.rm = TRUE as a matter of routine. It removes missing values without saying how many. An average of 3 values out of 4 is fine; an average of 3 out of 300 is not. When you see na.rm = TRUE, ask how many values were left out.

AI-written code often arranges the same pattern differently. These change how the code looks, not what it does:

  • One call inside another: round(mean(yields, na.rm = TRUE), digits = 1). Read from the inside out: first the average, then round it.
  • Spread over several lines: a long call, like data.frame(...) above, is split after commas. It is still one call; the closing ) ends it.
  • Inputs without names: round(3.14159, 2) is the same as round(3.14159, digits = 2), because digits is the second input. Named inputs are easier to read.
  • The pipe, |>: yields |> mean(na.rm = TRUE) means mean(yields, na.rm = TRUE). The object on the left becomes the first input of the function on the right. You will see it in nearly every chapter from Chapter 3 on.
yields |> mean(na.rm = TRUE)
[1] 161

Reading a help page

Every function has a help page. Put ? in front of its name, at the Console, and the page opens in the Help pane: ?seq. Three sections tell you most of what you need.

  • Description
  • Usage
  • Arguments, Examples, or ask

At the top, one or two sentences on what the function does. For seq(): “Generate regular sequences.” If that is not what you wanted, you are on the wrong page.

The function’s inputs, in order, each with its default. The real ?seq page also covers some related functions (seq_len(), seq_along() and others), so its Usage section lists several lines. The one for seq() itself is under ## Default S3 method:, a technical label you can ignore:

seq(from = 1, to = 1, by = ((to - from)/(length.out - 1)),
    length.out = NULL, along.with = NULL, ...)
  • Each name = value is an input and its default. Leave out from, and it is 1.
  • Inputs without names are matched by position: seq(0, 10) means from = 0, to = 10.
  • NULL means “not set”. ... means further inputs can be passed on; you can ignore it.

You only supply the inputs whose defaults you want to change. That is why seq(0, 10) works although seq() lists five inputs.

Arguments says what each input means. For seq(), by is the step between values and length.out is how many values you want, so the same sequence can be described two ways:

seq(0, 1, by = 0.25)
[1] 0.00 0.25 0.50 0.75 1.00
seq(0, 1, length.out = 5)
[1] 0.00 0.25 0.50 0.75 1.00

Examples, at the very bottom, is code you can copy and run. Running an example and then looking back at Usage is often the fastest way to understand a function.

You can also paste a line into an AI assistant and ask what each input does (see “Recommended requests”, tab “Explain code”). The help page is the reference to check its answer against: it describes the version of the function installed on your computer, which the AI cannot see.

Packages: installing and loading

  • What are packages?
  • Installing versus loading
  • When it goes wrong
  • Which package is a function from?

A package is a drawer in your workspace (the R environment) holding specialized tools (functions) for a particular set of tasks. Packages are written by R’s users and shared for free; most of the functions in this course come from them.

Example packages:

  • dplyr (data wrangling)
  • data.table (data wrangling)
  • ggplot2 (data visualization)
  • sf (spatial vector data handling)
  • terra (spatial raster data handling)
  • stars (spatiotemporal data handling)

tidyverse is a package that installs and loads a set of others at once, including dplyr, ggplot2 and readr.

Two separate steps:

  • Install: before you can use the tools (functions) in a drawer (package), you have to obtain the drawer. Installing downloads the package onto your computer. The name goes in quotation marks:
install.packages("ggplot2")
  • Load: you then bring the drawer into your workspace with library(). The name goes without quotation marks:
library(ggplot2)

You can now use the tools (functions) that drawer contains.

Install once, load every time

You install a package once per computer, at the Console. You load it with library() in every new R session (R from the moment it starts until it is closed or restarted), and that includes every time a Quarto document is rendered, because rendering starts a fresh R session. So library() lines belong at the top of your document, and install.packages() lines do not belong in it at all: they would download the package again at every render.

The two steps fail with two different errors, and the error tells you which step is missing:

library(notapkg)
Error in library(notapkg): there is no package called 'notapkg'

“There is no package called …”: the package is not installed (or the name is misspelled).

tidy_table <- as_tibble(yield_data)
Error in as_tibble(yield_data): could not find function "as_tibble"

“Could not find function …”: the package that has the function is not loaded (here, as_tibble() comes from the tibble package, which also comes with dplyr and tidyverse), or the function name is misspelled.

A line does not say which package its function comes from, unless it is written as package::function():

dplyr::filter(yield_data, yield > 225)

dplyr::filter means “the filter() function from dplyr”. It uses the function without loading the whole package, and it tells the reader where the function comes from. When you cannot tell, ask the AI, or run ?filter after the package is loaded: if several packages have a function of that name, the help pane lists them all, each with the package it comes from. Each help page also names its package at the top left, as in filter {dplyr}.

When code fails

Errors, and failures without one

  • Reading an error
  • Errors you will see
  • No error is not the same as right

When R cannot run a line, it stops and prints an error. Read it before anything else: it usually names the function that failed and what it objected to.

sum("a")
Error in sum("a"): invalid 'type' (character) of argument

“invalid ‘type’ (character) of argument”: sum() ran, but its input was text, and text cannot be added up.

Four errors you will see often:

The error says What it means Usual cause
object 'x' not found No object has that name A typo (R treats Yield and yield as different names), or the line that creates it was never run, or it was made in the Console but not in the document
could not find function "f" No loaded function has that name The package was not loaded, or a typo
there is no package called 'p' The package is not installed Not installed on this computer, or a typo
non-numeric argument to binary operator Arithmetic on something that is not a number A number stored as text

When you ask an AI about an error, send the whole error message, the code that produced it, and what you expected. The AI cannot see your screen.

An error is the good case: you know something went wrong. Worse are lines that run and give a wrong answer. Two you have already met:

  • One text value in c(...) turned every value to text, with no error.
  • na.rm = TRUE leaves out missing values without saying how many.

And one more. Text that looks like numbers is sorted as text, character by character:

sort(c("9", "10", "100"))
[1] "10"  "100" "9"

“10” comes before “9” because “1” comes before “9”. No error, wrong order. Checking the type of a value (class(), str()) would catch it.

Important

Code that runs is not the same as code that is right. Deciding whether it is right is the part that stays your job.

Asking AI

What the AI cannot know

The AI knows R. It does not know your session or your intentions. Each of these has to be in your request:

  1. The code: paste the exact lines, not a description of them
  2. What came out: the whole error message or output, copied, not retyped from memory
  3. What you expected: the result you thought you would get, and why
  4. What is around it: which objects already exist and what they hold, which packages you loaded. Running str() on an object and pasting the output is a quick way to describe it
  5. What you want back: an explanation, a corrected line, or both

Using an agent in your editor or terminal?

An agent such as Claude Code can run the code and see the error itself. Still say what you expected before it runs, so you have something to compare its answer with.

My R code doesn't work, please fix it.

The last paragraph is the closing instructions: the same lines end every request that asks for code. They make the AI put its code into a Quarto document, with a sentence above each piece of code, so that the result is a web page you can read and keep. Chapter 2 teaches Quarto; the full text is under “Recommended requests”.

here::here() builds a file’s path from the top folder of your project, so the path works on any computer. Chapter 3 explains it.

What the AI’s answer looks like in the rendered page: a sentence, then the code it describes. Read each sentence, and check that the code under it does what the sentence says.

mean() gives NA when any value is missing, unless told to leave missing values out with na.rm = TRUE.

average_yield <- mean(yields, na.rm = TRUE)

Print the checks: how many values there are, how many are missing, and the average of the rest.

cat(
  paste("values: expected 4, got", length(yields)),
  paste("missing values: expected 1, got", sum(is.na(yields))),
  paste("values used: expected 3, got", sum(!is.na(yields))),
  paste("average yield: expected 161, got", average_yield),
  sep = "\n"
)
values: expected 4, got 4
missing values: expected 1, got 1
values used: expected 3, got 3
average yield: expected 161, got 161

Every check matches, and each line says what it is checking. Two functions that may be new: cat() prints text, and paste() joins pieces of text into one. sum(!is.na(yields)) counts the values that are not missing (! means “not”).

Checking the result

Checking: what to ask for, and why

  • Checks you can know in advance
  • Asking for them
  • A check that fails

A check is only useful if you know the right answer before you see the result. The AI can write the checking code; only you can supply the answer. Sources of answers you know in advance:

Ask the AI to print You know the answer from
1 how many values, rows or columns there are counting, or the description of the data (a help page, a codebook)
2 the type of each key value or column knowing what it measures: a yield is a number, a state name is text
3 how many values are missing the data’s description, or counting them yourself on a small case
4 the smallest and largest value what is believable: a corn yield is not negative
5 the result on a small case working it out by hand, as for the average of 150, 162 and 171

Say what you expect, and ask for each check in one form, so the rendered page says which passed:

I expect <number> values, <number> of them missing, and an average of
<number>. Print each check on its own line as "name of check: expected
X, got Y".

If you cannot fill in a blank, that is a sign to look at the data, or its description, before asking.

A student expected the values to be numbers. The AI’s code, and what it printed:

Code the AI wrote 
cat("type of mixed: expected numeric, got", class(mixed), "\n")
type of mixed: expected numeric, got character

The check fails: mixed holds text. Nothing errored, and any average of it would be wrong or NA. The right move is to find out where the text came from (here, the "5" written in quotation marks) before going on.

Your turn: read the AI’s code

A student asked an AI to “average my yields”, and got this:

library(dplyr)
my_yields <- c(150, 162, "171", 140)
avg = mean(my_yields)
avg
  • Questions
  • Answers

A. What does each of the four lines do?

B. What will avg print, and why? Is there an error?

C. Which check from the previous slide would have caught the problem, and what would it have printed?

D. Is line 1 needed?

A. Loads the dplyr package; stores four yields under the name my_yields; computes their average and stores it as avg (= does the same as <- here); prints avg.

B. NA. Because "171" is in quotation marks, the whole vector is text, and the average of text is NA. There is no error, only a warning (“argument is not numeric or logical: returning NA”), which is easy to miss.

C. Check 2, the type: “type of my_yields: expected numeric, got character”.

D. No. None of the functions used (c(), mean()) comes from dplyr; both are built into R. It does no harm, but a line you cannot explain is worth asking about.
